# Decisions

Product decisions for ClearFEA, from the interview of 2026-10-13, followed by a log of architecture decision records (ADRs). This file is the source of truth for scope. Change it only through a pull request that explains why.

## Purpose and users

- ClearFEA is an online FEA platform in the style of SimScale, with published compute-based pricing. It is a community project that aims to break even.
- It is a fresh project, separate from the earlier Code_Aster platform idea.
- **Primary user:** working engineers without a licence (freelancers, small-firm and EPC engineers). They know FEA basics and need a trustworthy result and a report.
- **Acceptance test:** the maintainer can run his own static-equipment work on it.
- **Name:** ClearFEA. Domain, GitHub organisation and trademark checks are still open.

## Scope at the Phase 0 gate

## Platform decisions

- **Prototype shape.** Cloud-shaped and run locally: web frontend, an API written for Cloudflare Workers (run in its local emulator with local D1 and R2), and a separate containerised job worker. The same container runs on AWS in Phase 1.
- **Where compute runs.** STEP import and meshing run on the server in the worker container. Import is free. Meshing is metered at the same rate as solving.
- **Data structure.** Project → simulations → runs. A run is a frozen snapshot of setup, mesh, solver input, log, results and cost. Meshes are reused across runs when mesh settings are unchanged.
- **Accounts in Phase 0.** Every record has an owner. Simple local login with two or three seeded test users. No email, no password reset.
- **Running jobs.** Stage, elapsed time, running cost against estimate, live solver log, cancel button, automatic stop limit per run (a multiple of the estimate, user adjustable). Jobs continue when the browser is closed.
- **Privacy.** Private by default. Read-only share link per run, revocable. Opt-in public gallery. Uploaded geometry is used only to run the user's jobs. Operator access only for support the user requested.
- **Self-hosting.** First-class and documented, using the same one-command setup. Wallet and metering off or informational. Community-only support.
- **Positioning.** A general-purpose analysis tool. Reports carry software and solver versions and a link to verification results. The platform never prints a pass/fail or code-compliance verdict.

## Pricing decisions

- **Unit of charge.** Machine-seconds on a short published list of machine sizes, each with a published hourly rate. Billed per second while the job occupies the machine. Queue waiting and machine start-up are not billed.
- **Mark-up.** Internal, not published. Rates are set from beta cost data to cross break-even.
- **Size recommendation.** The platform recommends a machine size from the mesh estimate. The user may override it.
- **Failed runs.** The user pays for time used when the cause is their setup or choice (under-constrained model, mesh failure on their geometry, out of memory on a size they chose against the recommendation, cancellation). The platform absorbs its own faults (machine lost, internal error, storage or queue failure, out of memory on a size it recommended). Each failed run shows its category and reason.
- **Pre-run checks.** Free validation before any machine is used: model restrained, every body has a material, loads reference existing faces.
- **Storage.** Free allowance per user. Lightweight items (geometry, setup, solver input, logs, report, viewer data) kept permanently. Raw solver output removed after a fixed period unless the run is pinned; it can be regenerated by rerunning. Storage above the allowance charged at a published rate.
- **Phase 0 wallet.** Real metering and a real ledger with play-money balances. No payment provider.
- **Beta.** Free, with a per-user monthly credit grant and a global budget cap that stops new runs when reached.
- **Beta compute.** One fresh on-demand machine per job, destroyed afterwards. Designed so that a cheaper spot tier can be added.

## Process decisions

- **Licence.** AGPL v3.
- **Contributions.** Developer Certificate of Origin sign-off on every commit. No contributor licence agreement.
- **Repository.** Public from the first commit. Decisions and roadmap live in the repository.
- **Workflow.** All work on branches, merged through pull requests.
- **Test tiers.** Pull requests run unit and snapshot tests, type checks and lint. Physics verification and browser tests run nightly and at milestones.
- **Verification.** Automated benchmark suite through the full platform path, with results and errors published. Every load and support type has at least one case.
- **Build order.** Thin end-to-end slice first, then widening milestones (see `PLAN.md`).
- **Acceptance cases.** (A) Nozzle-to-shell junction with reinforcing pad under pressure and nozzle loads. (B) Thermal stress in a component with a through-wall temperature gradient. Run at the end of Phase 0. Checked against hand calculations and an independent FreeCAD FEM setup.
- **Beta.** Invite-only, 10 to 20 engineers, 8 to 12 weeks, with stated goals.

## Phase 0 is done when

1. Both acceptance cases are completed entirely through the UI on the laptop (i5 10th gen class, 16 GB RAM), with reactions balanced, results within tolerance of hand checks and the FreeCAD run, and a report fit to hand to a reviewer.
2. The full verification suite is green, with every gate load and support type covered.
3. Cost estimates are within the agreed margin of measured cost on the benchmark set, and the wallet ledger reconciles exactly.
4. A model at each solver's element limit (ADR-063) is run on the laptop, with a responsive viewer.
5. A fresh clone starts the whole system with one documented command.
6. Data isolation between test users is proven by automated tests.
7. A short user guide covers the main flow.
8. Two or three outside engineers complete a provided tutorial case unaided.

Working tolerances, to be tuned from benchmark data: results within 5 percent of the FreeCAD run on a matching mesh; cost estimates within 30 percent of measured cost.

## After the gate

In order:

1. Shells from surface bodies with user-assigned thickness
2. Face splitting
3. Stress linearisation (membrane, bending, peak) along a path
4. Run comparison table for mesh convergence
5. Geometry revisions that carry loads over to a new STEP version
6. Nonlinear milestone: contact, elastic-plastic materials, large deformation, buckling

Before or during the beta: first-run guided overlay, email notifications, real authentication.

After the beta: team workspaces, user-defined acceptance checks in reports, bring-your-own-input jobs as a separate job type, real payments, spot-priced economy tier.

## Non-goals for Phase 0 and the beta

1. No fluid simulation, electromagnetics or other physics.
2. No nonlinear analysis: contact, plasticity, large deformation, buckling.
3. No transient thermal or dynamic response analysis.
4. No shells, beams or mixed-element models.
5. No geometry creation or editing.
6. No IGES, STL or mesh import.
7. No hexahedral meshing or adaptive refinement.
8. No editing of solver input, and no bring-your-own-input jobs.
9. No built-in code compliance checks or bundled code material data.
10. No team workspaces, real-time collaboration or comments.
11. No real payments, invoices or spot-priced tier.
12. No public API, scripting or CAD plug-ins. The internal API is kept clean so a public one is cheap later.
13. No mobile or tablet layout for setup.
14. No interface languages other than English.
15. No optimisation, parametric studies or fatigue.

## Architecture decision records

### ADR-001: Monorepo with three deployable parts
2026-10-13 · accepted 2026-10-14

`apps/web` (frontend), `apps/api` (Cloudflare Worker), `worker` (Python container), plus `packages/spec` for shared schemas. One repository keeps the spec, the deck generator and the UI in step.

### ADR-002: Gmsh as both geometry importer and mesher
2026-10-13 · accepted 2026-10-14

Gmsh, through its OpenCASCADE kernel, reads the STEP file, supplies the display tessellation and produces the mesh. One tool owns face identity from import to mesh, which is the riskiest chain in the product. Gmsh is GPL, compatible with AGPL.

### ADR-003: SI base units as the internal system
2026-10-13 · accepted 2026-10-14

All stored and solved quantities are in m, kg, s, K. Gmsh converts STEP geometry to metres at import. One rule with no exceptions is easier to keep correct than a mm-tonne system. Entered values are stored with their unit as typed; conversion uses one shared table.

### ADR-004: Jobs table with a claim API instead of a managed queue
2026-10-13 · accepted 2026-10-14

Jobs live in D1. The worker claims work over HTTPS from the API. This behaves identically on localhost and in the cloud, and avoids depending on local emulation of Cloudflare Queues. A managed queue may still trigger machine launches in Phase 1.

### ADR-005: Worker moves files through transfer URLs issued by the API
2026-10-13 · accepted 2026-10-14

The worker never holds storage credentials. For each job the API issues upload and download URLs. Locally these point at API pass-through endpoints; in the cloud they are presigned R2 URLs, which avoids Worker body-size limits.

### ADR-006: SimulationSpec as a versioned JSON document
2026-10-13 · accepted 2026-10-14

A simulation's setup is one JSON document validated by JSON Schema in `packages/spec`. TypeScript types and Pydantic models are generated from the schema. Runs store a frozen copy.

### ADR-007: React, Vite, TypeScript and three.js for the frontend
2026-10-13 · accepted 2026-10-14

Widely used, well supported by Claude Code, and three.js is sufficient for surface rendering with per-face picking.

### ADR-008: Hono on Cloudflare Workers with D1 and R2
2026-10-13 · accepted 2026-10-14

Matches the deployment target in the brief. Wrangler's local mode provides D1 and R2 on localhost.

### ADR-009: Python for the worker
2026-10-13 · accepted 2026-10-14

Gmsh has a first-class Python API, and Python has mature libraries for numerical work and document generation.

### ADR-010: Start with the distribution CalculiX build; choose the production solver build by benchmark
2026-10-13 · accepted 2026-10-14

Milestone M1 uses a packaged `ccx` (SPOOLES). A benchmark task in M2 compares SPOOLES, PaStiX and the iterative solver for speed and memory, then fixes the build for the 2-million-element target. Building CalculiX with PaStiX is known to be fiddly, so it is isolated as its own task. (ADR-063 replaced the packaged build with one including PaStiX, the default solver, and dropped the 2-million-element target.)

### ADR-011: Report figures are captured in the browser
2026-10-13 · accepted 2026-10-14

Report pictures are rendered by the same three.js viewer and uploaded as images when the user generates a report. One renderer keeps reports consistent with what the user saw. The cost is that report generation needs the browser open.

### ADR-012: Docker runs in the cloud environment; the worker stays a container
2026-10-14 · accepted 2026-10-14

M0.1 found that Docker works in the Claude Code cloud environment, so the plain-process fallback is not needed and the worker stays a container as in `ARCHITECTURE.md`. Three conditions apply there. The daemon is not started for us, so a session starts `dockerd` in the background before using Docker. Anonymous pulls from Docker Hub fail with HTTP 429, so base images are named through the public `mirror.gcr.io/library/` mirror, which serves the same official images and needs no account, so it works on the laptop too. HTTPS traffic leaves through a proxy with its own certificate authority, so a build that downloads over HTTPS (pip) reads that certificate from an optional BuildKit secret (`--secret id=extra_ca`) at build time; the certificate is never copied into an image layer or the repository, and builds without the secret work unchanged on the laptop.

### ADR-013: Python tooling lives in `worker/`; versions pinned per workspace
2026-10-14 · accepted 2026-10-14

The `uv` project is `worker/pyproject.toml` with its own `uv.lock`, not a uv workspace at the repository root, because the worker is the only Python package. Python is pinned to 3.12 there (`.python-version`, `requires-python`), and dev tools (pytest, ruff) are pinned to exact versions. TypeScript packages are a pnpm workspace (`apps/*`, `packages/*`) with pnpm pinned through `packageManager`. If verification scripts later need their own Python package, the root becomes a uv workspace with `worker` as a member.

### ADR-014: API tests run inside the Workers runtime against local D1 and R2
2026-10-14 · accepted 2026-10-14

API tests use Vitest with `@cloudflare/vitest-plugin` (the renamed `@cloudflare/vitest-pool-workers`), which runs each test file in the same `workerd` runtime and with the same D1 and R2 emulation as `wrangler dev`, configured from `apps/api/wrangler.jsonc`. Migrations from `apps/api/migrations` are applied before each test file, and storage is isolated per test, so tests need no running server and no mocks of D1 or R2. The alternative, mocking the bindings in Node, is simpler to set up but would not catch SQL or binding behaviour that differs from the real runtime. TypeScript dependencies are pinned to exact versions, and the plugin, `wrangler` and `@cloudflare/workers-types` are chosen so they share one `workerd` build. pnpm's default supply-chain policy refuses packages published in the last day, so new versions are taken only after that delay rather than by adding exclusions.

### ADR-015: Worker image on Ubuntu 24.04 with CalculiX 2.21 and Gmsh 4.15.2
2026-10-14 · accepted 2026-10-14

The worker image is built on `ubuntu:24.04`, pinned by digest and pulled through `mirror.gcr.io` (ADR-012). Its system Python is 3.12, matching ADR-013. CalculiX is the distribution package `calculix-ccx=2.21-1` from the noble release pocket, which does not change after release, so the pin stays installable. Gmsh is the PyPI wheel `gmsh==4.15.2`, recorded in `worker/uv.lock` so the host and the image install the same file; the wheel bundles its own OpenCASCADE. M0.1 probed `python:3.12-slim-bookworm`, but Debian bookworm ships CalculiX 2.20 and Debian trixie has no `calculix-ccx` package at all, while the Claude Code cloud host is Ubuntu 24.04 with 2.21. Choosing the same base as the host means a case run locally in a session and in the container uses the same solver build. Cost: the image is about 990 MB, mostly LLVM and GPU libraries pulled in by Mesa (for Gmsh's `libGLU` dependency) and by Open MPI (a `calculix-ccx` dependency), against about 490 MB for the bookworm probe. Image size is a gate target (M9), not an M0 one.

### ADR-016: Worker authenticates with a shared token; on Linux it uses host networking locally
2026-10-14 · accepted 2026-10-14

The `/internal` routes accept a bearer token compared against the API's `WORKER_TOKEN` secret (`apps/api/.dev.vars` locally, a Workers secret in the cloud); the worker sends it from `CLEARFEA_WORKER_TOKEN`. One shared token is the simplest thing that keeps user sessions and worker access apart; per-machine tokens can replace it in Phase 1 when machines are launched per job. Worker data-access functions are scoped to the claiming worker's id rather than a user id, because the worker serves every owner; they can only touch jobs that worker has claimed. Locally, `wrangler dev` listens on loopback only. Docker Desktop forwards `host.docker.internal` to the host's loopback, but Docker Engine on Linux does not, so `infra/docker-compose.linux.yml` puts the worker on the host network instead of exposing the API on every interface.


### ADR-017: Schema code generation and runtime validation in `packages/spec`
2026-10-14 · accepted 2026-10-14

Schemas are JSON Schema draft 2020-12, one file per area, with the messages of an area under `$defs`. TypeScript types come from `json-schema-to-typescript`; a small script adds a typed `validateX` function for every schema and definition and a `XValues` list for every enum. Runtime validation in TypeScript uses `@cfworker/json-schema`, because it interprets schemas without generating code, which Cloudflare Workers forbid (Ajv compiles validators with `new Function` unless its validators are pre-built in a separate step). Pydantic v2 models for the worker come from `datamodel-code-generator`, with snake_case fields aliased to the camelCase wire names. Generated files are committed rather than built on install, so the worker image and the apps need no generation step, and `make test` regenerates both into a scratch location and fails if the committed files differ (`make spec` rewrites them). The alternative of generating at build time keeps generated code out of review but adds a build step to every consumer, including the Docker image.

### ADR-018: Units table format
2026-10-14 · accepted 2026-10-14

`packages/spec/units.json` maps each quantity kind to its SI unit and to the allowed units, each with a `factor`, an optional `offset` (value in SI = value × factor + offset) and a `definition` naming where the factor comes from, so a reviewer can check every number. The table is versioned. Unit symbols are case-sensitive keys (`MPa`, not `mpa`). Both loaders refuse a table whose SI unit is not listed with factor 1 and no offset. Factors that are not exact in binary (psi, ksi) are written as the double nearest the exact value. M0.6 defines length (m, cm, mm, in, ft), force (N, kN, MN, lbf, kip) and pressure (Pa, kPa, MPa, GPa, bar, psi, ksi); later kinds are added with the feature that needs them. A shared fixture of hand-worked conversions is run in both languages in both directions with a relative tolerance of 1e-12.

### ADR-019: Biome is the one TypeScript lint tool
2026-10-14 · accepted 2026-10-14

All TypeScript and JavaScript in `apps/` and `packages/` is linted by Biome (`@biomejs/biome`, pinned) with its recommended rules, from one `biome.json` at the root; `make lint` and `make test` run it with warnings treated as errors. Generated code in `packages/spec/src/generated` is excluded. Biome is one dependency and one config file and needs no plugins for TypeScript or React. The alternative, ESLint with typescript-eslint and the React plugins, has more rules (including type-aware ones) but needs several packages kept in step and a slower run. Formatting is not enforced for now: turning on Biome's formatter would rewrite most existing files, so it is a separate decision. If a rule Biome lacks is needed later, ESLint can be added for that rule alone.

### ADR-020: `make dev` is a shell script that supervises three processes
2026-10-14 · accepted 2026-10-14

`make dev` runs `infra/dev.sh`, which starts `wrangler dev` and Vite on the host and the worker through Docker Compose, prefixes each line of output with the service name, and stops all three when any one exits or on Ctrl-C. It checks first that dependencies are installed, Docker is reachable and ports 8787 and 5173 are free, and says what to do if not. It creates `apps/api/.dev.vars` from the example when missing and passes its `WORKER_TOKEN` to the worker, so the two cannot disagree (ADR-016). On Linux without Docker Desktop it adds the host-networking override. A plain Bash script needs no new dependency; the alternatives were an npm process runner such as `concurrently` (one more package and it does not manage the Compose service) or running the API and web app in Compose too (slower reloads, and `wrangler dev` state would live in a container).

### ADR-021: CI runs `make test` on GitHub Actions with pinned actions; the DCO App checks sign-offs
2026-10-14 · accepted 2026-10-14

`.github/workflows/fast.yml` runs on every pull request: one job runs `make install` and `make test` on `ubuntu-24.04`, so CI and a contributor's machine run the same commands and there is no second list of checks to keep in step. Every third-party action is pinned to a full commit SHA with the version in a comment, because a tag can be moved to different code, and the workflow token is read-only. Node 22, pnpm (from `packageManager`), uv 0.11.32 and Python 3.12 match the cloud session. DCO sign-off is checked by the DCO GitHub App, which is already installed on the repository; an in-repo script doing the same check was written and then dropped at the maintainer's choice so each pull request has one sign-off check. `.github/workflows/nightly.yml` is a scheduled placeholder that does nothing until `make verify` (M1.13) and `make e2e` (M1.14) exist.

### ADR-022: Phase 0 login is a seeded password table and a stateless signed cookie
2026-10-14 · accepted 2026-10-14

Two test users, `alice` and `bob`, are seeded into the local D1 from `apps/api/seed/test-users.sql` by `pnpm --filter @clearfea/api db:seed`, which `pnpm --filter @clearfea/api dev` (and so `make dev`) runs after the migrations. The seed is not a migration, so it can never reach a cloud database. Their passwords (`alice-local`, `bob-local`) are documented in the seed file: they protect nothing but local test data. Migration 0003 adds `users.password_hash`, PBKDF2-SHA256 with 100 000 iterations and a random salt through Web Crypto, because Workers have no bcrypt or scrypt and cap PBKDF2 at 100 000 iterations. `POST /api/session` checks the password and sets an `HttpOnly`, `SameSite=Lax` cookie holding the user id and an expiry seven days out, signed with HMAC-SHA256 under `SESSION_SECRET` from `apps/api/.dev.vars`; `Secure` is added when the API is reached over HTTPS. The cookie is stateless: there is no sessions table, so signing out clears the cookie but cannot revoke a copied one before it expires, which is acceptable for local test users. Every signed-in route goes through one middleware (`requireUser` in `apps/api/src/session/`), which also checks that the user still exists, and puts the user id in the request context; routes never read the cookie, so real authentication replaces that module in Phase 1 without touching them. Public request bodies must be sent as `application/json`, which a cross-site HTML form cannot do without a preflight the API never grants. A wrong password and an unknown login get the same answer and take the same time. The alternatives were a user picker with no password (simpler, but nothing to test the login path against) and a sessions table (revocable, but one more table and a lookup the stateless cookie avoids).

### ADR-023: Face identity chain confirmed; the import job reads the STEP length unit itself
2026-10-14 · accepted 2026-10-14

The M1.1 spike (`worker/spikes/face_identity/`) ran the chain in `ARCHITECTURE.md` section 3 on a block, a flanged pipe with filleted joints and bolt holes, and a filleted L bracket with holes, each declared in mm, m and in, with every step in its own process. Gmsh 4.15.2, OpenCASCADE 7.8, one thread. Results and the method are in the spike's README. Findings, and what M1.2 and M1.6 should build on them:

1. **Gmsh does not report the file's length unit.** It converts coordinates to `Geometry.OCCTargetUnit` correctly, but neither the API nor its log names the unit the file declared. The import job therefore reads it from the STEP data section: the length unit referenced by `GLOBAL_UNIT_ASSIGNED_CONTEXT`, either `SI_UNIT` on `METRE` (no prefix, `CENTI`, `MILLI`) or a `CONVERSION_BASED_UNIT` named `INCH` or `FOOT`. Only the unit's symbol is taken from the file and factors come from `units.json`; a conversion-based unit's own factor is cross-checked against the table and refused if they differ. No declared unit, several different ones, or an unsupported one (for example micrometres) gives no detected unit, and the user must choose one before the geometry can be used. Nothing is guessed.
2. **Import with `Geometry.OCCTargetUnit = "M"`.** Gmsh's default is OpenCASCADE's millimetres, so ADR-003's "Gmsh converts STEP geometry to metres" holds only with this option set. With it, the m and in variants matched the mm model scaled by the `units.json` factor to 1e-15.
3. **A unit the user corrects is applied by re-importing with `Geometry.OCCScaling`**, the ratio of the confirmed to the declared factor, not by scaling after import. `occ.dilate` turns every face into a B-spline approximation: face types change and areas move by up to 0.3 percent. Re-importing with `OCCScaling` keeps tags, types, areas and centroids to 1e-15. The geometry record stores the declared unit, the confirmed unit and the scaling, and every later job imports with the same options.
4. **Face tags are stable across processes.** Re-importing the same file in a fresh process gave the same tags with identical areas, centroids, types and parent bodies (difference 0), so the mesh job's comparison with `topology.json` can use a tight tolerance (1e-9 of the model size).
5. **Face-to-element mapping is a lookup.** Gmsh's surface triangles share nodes with the tetrahedra, so each surface triangle matches the boundary tetrahedron face with the same corner nodes. For first- and second-order meshes of all nine inputs, every surface triangle found its tetrahedron face, every boundary tetrahedron face had a face tag, and every mapped face lay on its own CAD face and closer to it than to any other face.
6. **The display mesh is a separate, curvature-sized surface mesh** of the same import, stored as float32 positions with triangles grouped by face tag. Read back, every triangle lay on its own face.

Not covered, for later tasks: CalculiX's face numbering of C3D4 and C3D10 elements (the spike records Gmsh's local face index; M1.7 maps it and checks it against the CalculiX manual), multiple bodies and the tag renumbering that `fragment` causes (M4), and STEP files exported by commercial CAD systems (the test files were written by OpenCASCADE with the unit entity edited). Meshing was run single-threaded; the same input gave the same element count in separate processes and repeated runs, but the same shape declared in different units gave slightly different meshes (842 to 864 tetrahedra for the block), so a mesh is reproducible only for the same imported geometry. The spike uses numpy through `uv run --with`; adding it as a worker dependency is left to the task that first needs it in job code.

### ADR-024: The import job applies the STEP unit through OpenCASCADE's reading factor; jobs move files through per-job transfer routes
2026-10-14 · Accepted (auto-approved under Shubham's standing M1 instruction; reviewed and accepted by Shubham on 2026-10-16)

M1.2 turns ADR-023 into the `import` job, the geometry routes and the upload panel. Decisions it needed:

1. **Reading factor.** To apply a unit the user chooses, the job must know how OpenCASCADE scaled the file when it read it as it is. Experiments with Gmsh 4.15.2 and OpenCASCADE 7.8.1: a file that declares no length unit is read as if its coordinates were already in the target unit (100 in the file became 100 m with `OCCTargetUnit = "M"` and 100 mm with `"MM"`), and a conversion-based unit is applied with the file's own factor even when its name is unknown or its factor disagrees with `units.json` (a unit named `WIDGET` defined as 25 mm was read as 25 mm). The import job records this reading factor (metres per file coordinate) and applies a chosen unit by re-importing with `Geometry.OCCScaling` = the chosen unit's factor from `units.json` ÷ the reading factor. So the user can choose the unit for a file with no unit, an unknown named unit or a disagreeing inch, as ADR-023 asks. Two cases have no known reading factor and fail as the user's fault, asking for a re-export in a supported unit: an SI prefix the units table does not list (for example micrometres, which OpenCASCADE applies but for which ClearFEA has no factor without hard-coding one), and a file declaring several different length units. This narrows ADR-023 point 1, which let the user choose in every case. `worker/tests/test_geometry_import.py` pins the no-unit behaviour, so a Gmsh or OpenCASCADE upgrade that changes it fails the fast tier.
2. **Geometry life cycle.** `importing` → `needs_unit` (no detected unit) or `unconfirmed` (detected) → `ready` once the user confirms; `failed` with a plain-language problem. Confirming the unit the topology was made at needs no job; any other unit queues a re-import, and only the geometry's latest import job may update it, so a late answer from an older job is ignored. Until simulations reference faces (M1.4), the unit of a ready geometry can still be changed; M1.4 or M1.5 must lock it once a simulation uses the geometry. Projects have no routes yet, so a geometry's `project_id` is null for now and the web app shows the user's most recent geometry.
3. **Upload.** `POST /api/geometries?name=…` takes the file as the raw body with `Content-Type: application/octet-stream`, which a cross-site HTML form cannot send without a preflight the API never grants (the same protection as ADR-022's JSON rule). The alternative, a multipart form, would need a CSRF token. Files are limited to 100 MB, the Workers request-body limit; larger files will need direct-to-storage upload in Phase 1. The API checks only that the body starts with `ISO-10303-21`; everything else is the worker's job.
4. **Transfers (ADR-005 in practice).** A claimed job now carries `params` and `transfers` (`name`, `direction`, `url`). In Phase 0 the URLs point at `GET`/`PUT /internal/jobs/:id/files/:name?worker=<id>`, which need the worker token, accept only the worker holding the job, and only the names its type defines (`apps/api/src/jobs/files.ts`). The worker sends its token only to the API's own `/internal/` URLs, so presigned storage URLs can replace these in Phase 1 without a worker change. Files are stored under `owners/<owner>/geometries/<id>/` as `model.step`, `topology.json` and `display.bin`. A succeeded import whose result does not match `ImportResult` or whose outputs are missing is recorded as a platform fault, so a geometry never becomes ready on outputs the viewer cannot read. Failed jobs may carry a `failureMessage` for the user next to the cause code.
5. **Display mesh format.** Version 1 is `packages/spec/display-mesh.md`. Unlike the spike's file, each face owns its run of vertices, so the viewer can shade a face smoothly and keep a sharp edge between faces.
6. **Gmsh in CI.** The fast tier now installs the system libraries the Gmsh wheel loads (the same list as `worker/Dockerfile`), because the import tests run Gmsh; Shubham approved this CI change in the M1.2 thread.
7. **Units table in the worker image.** The image copies `packages/spec/units.json` from a named build context (`--build-context spec=packages/spec`, `additional_contexts` in Compose), so the build context stays `worker/` and the table stays single.

Not done here: a heartbeat timeout that fails a job whose worker died (an import whose worker crashes leaves its geometry `importing`), and running Gmsh in a child process so a crash on a malformed file cannot take the worker down. Both are worth doing before files from outside the project are imported.

### ADR-026: SimulationSpec v1 is a draft-friendly document with inline materials; a used geometry's unit is locked
2026-10-15 · Accepted (auto-approved under Shubham's standing M1 instruction; reviewed and accepted by Shubham on 2026-10-16)

M1.4 defines `SimulationSpec` version 1 (`packages/spec/schemas/simulation.schema.json`) and the routes that store it. Choices it needed:

1. **Shape.** `{ version: 1, analysis: "linear_static", geometryId, bodies, materials, supports, loads, mesh }`. `bodies` lists every body of the geometry once with the id of its material (ARCHITECTURE section 4's "per-body material assignment"). Materials (`isotropic_elastic`: Young's modulus, Poisson's ratio), supports (`fixed`) and loads (`pressure`) are arrays of items with a client-chosen `id`, unique across the spec, a `name` and a `type`, so later types join the same arrays (a `oneOf` per array once there are two). `mesh` holds the global `size`. Density, element order and solver options are left out until a task needs them (gravity in M2.3, element order in M2.8); adding a field is a schema change like any other.
2. **Quantities** are `{ value, unit }` as typed (ARCHITECTURE section 4). The schema cannot list the units of a kind without copying `units.json`, so it only requires a unit string; `checkSimulationSpec` in `packages/spec/src/simulation.ts` refuses a unit that is not of the field's kind (Young's modulus and pressure: pressure; mesh size: length), using the one table. Poisson's ratio is a plain number in (-1, 0.5), which the schema checks.
3. **Draft-friendly.** Every value may be `null` and every face list empty, so the M1.5 panels can save each edit and the tree can mark items incomplete. Saving refuses only what is wrong, not what is missing: a malformed document, a unit of the wrong kind, a zero or negative modulus or mesh size, a repeated id, a body assigned a material that is not listed, a body or face tag the geometry does not have, or a geometry body missing from `bodies`. What a run still needs is pre-run validation (M1.12).
4. **Pressure sign.** A positive pressure pushes on the face towards the body, as a fluid does; negative is suction. The deck generator (M1.7) must map this to CalculiX's convention and a verification case must prove it.
5. **Materials are copied into the spec**, not referenced, so a run's frozen spec (ADR-006) never changes when a library or custom material does (M2.9 copies from the library into the spec).
6. **Storage and routes.** Migration 0005 adds `simulations` (owner, geometry, name, `analysis_type`, `spec_version`, the spec as JSON). `POST /api/simulations { geometryId, name, spec? }` needs a `ready` geometry and starts from an empty spec listing the geometry's bodies when `spec` is left out (the verification harness, M1.13, can pass a whole spec). `GET /api/simulations[?geometryId=]`, `GET /api/simulations/:id` and `PUT /api/simulations/:id/spec` (whole-document replace, last write wins) complete the set; a spec cannot move to another geometry. Each save reads the geometry's `topology.json` to check tags.
7. **Unit lock.** Once a simulation uses a geometry its unit can no longer change, since a re-import at another scale would move every face the spec refers to: `POST /api/geometries/:id/unit` answers 409 for any other unit, `GeometryView.unitLocked` tells the web app to hide the unit control, and the database refuses to delete a geometry a simulation uses. This settles the open point in ADR-024 item 2. The unit can still be changed until the first simulation is created; the insert and the unit change each check the other in their own statement.

Not done here: a Python counterpart of `checkSimulationSpec` (the Pydantic model checks the shape; the deck generator, M1.7, converts units through `units.py`, which refuses a unit of the wrong kind, and should also refuse repeated faces, which Pydantic does not check), optimistic concurrency on saves, renaming and deleting simulations, and projects.

### ADR-028: The mesh job meshes the confirmed geometry with second-order tetrahedra of one global size and writes its own mesh file
2026-10-15 · Accepted (auto-approved under Shubham's standing M1 instruction; reviewed and accepted by Shubham on 2026-10-16)

M1.6 adds the `mesh` job (`worker/clearfea_worker/meshing/`), the `meshes` table and routes, and the Mesh item of the setup tree. Choices it needed:

1. **Second-order tetrahedra only, for now.** Every Phase 0 mesh is 10-node tetrahedra (`ElementOrder` 2, CalculiX C3D10) until M2.8 offers the choice; first-order tetrahedra are too stiff for stress results. Mid-edge nodes lie on the curved CAD faces (`Mesh.SecondOrderLinear = 0`). The order travels in the job parameters and the mesh file, so M2.8 adds a field, not a format.
2. **One global size.** `Mesh.MeshSizeMax` is the size the user entered; sizes from CAD points and from curvature are off, so the size field means what it says (local sizes are M2.8). Gmsh runs single-threaded, as in the import (ADR-023). The size is stored and sent as typed (`{ value, unit }`) and converted to metres by the worker through `units.py`.
3. **Face identity is checked before meshing.** The job re-imports `model.step` with the geometry's `scaling` and compares every face's area, centroid, Gmsh type and parent bodies, and each body's faces, with `topology.json` at a relative tolerance of 1e-9 (ADR-023 item 4). Any difference fails the job as a platform fault (`topology_mismatch`), per ARCHITECTURE section 3.
4. **Own mesh file.** `mesh.bin` (`packages/spec/volume-mesh.md`) holds float64 node positions, the elements by body in Gmsh's node order, and for each face tag its element faces as (element, local face) pairs, found by matching each surface triangle's corner nodes to a tetrahedron face (ADR-023 item 5). The deck generator (M1.7) reads it without Gmsh and maps Gmsh's node order and local faces to CalculiX's. The viewer gets a separate `display.bin` of the mesh's surface in the display mesh format (corner nodes only), so the existing reader, picking and face colouring work unchanged.
5. **Guards.** A size whose estimate (6 × volume ÷ size³, on the high side of the 4.5 measured) exceeds 2,000,000 elements, the design target in DECISIONS, is refused before meshing as the user's fault, with the smallest size that passes, rounded up. Elements with a zero or negative scaled Jacobian, and a Gmsh failure, are also the user's fault, with a request to try a smaller size. No quality summary yet (M2.8).
6. **Records.** A mesh row holds the geometry, the size as typed, the order, status (`meshing`, `ready`, `failed`), counts and its job; files are `owners/<owner>/meshes/<id>/`. `simulations.mesh_id` points at the simulation's latest mesh. `POST /api/simulations/:id/mesh` meshes with the size of the saved spec (the panel's button waits for "All changes saved") and is refused while that simulation's mesh is still being made; every request makes a new mesh until reuse by settings hash (M2.10). Mesh shapes live in `simulation.schema.json`, because the code generators do not resolve references between schema files and the shapes need `Quantity`.
7. **Showing it.** The tree gains a Mesh row: incomplete until a size is entered and a mesh exists for that size, incomplete while meshing, error with the reason when meshing failed. The panel offers the geometry's own unit first. While the Mesh row is open and the latest mesh is ready, the viewer draws the mesh surface with every element edge and "Mesh: N elements, M nodes"; switching between geometry and mesh keeps the camera. Meshing is not metered until M1.11 and cannot be cancelled yet.

### ADR-029: The deck generator writes one deterministic CalculiX deck from the spec and the mesh file
2026-10-15 · Accepted (auto-approved under Shubham's standing M1 instruction; reviewed and accepted by Shubham on 2026-10-16)

M1.7 adds the deck generator (`worker/clearfea_worker/deck/`), a pure function `generate_deck(spec, mesh) -> str` from a `SimulationSpec` and a `mesh.bin` (ADR-028). Choices it needed:

1. **Element mapping from the manual, checked by solving.** CalculiX numbers C3D10 mid-edge nodes on edges 1-2, 2-3, 3-1, 1-4, 2-4, 3-4, so Gmsh's last two mid-edge nodes swap (with Gmsh's own order CalculiX stops on a non-positive Jacobian). Gmsh local faces 0, 1, 2, 3 are CalculiX faces 1, 2, 4, 3 (manual section 7.43: 1-2-3, 1-4-2, 2-4-3, 3-4-1). Both tables are derived in `deck/elements.py` from the manual's lists rather than typed in, and tested geometrically.
2. **Pressure sign.** A positive CalculiX pressure pushes against the face's outward normal, which is ADR-026's convention, so the entered value is written unchanged. Shown by solving: positive pressure on each face of a bar gives a reaction of +p·A·n and shortens the bar by p·L/E (`worker/spikes/deck_check/`, 28 checks). That script stands in until V-01 and V-02 run under `make verify` (M1.13).
3. **Deck layout.** All mesh nodes (`NALL`), one element set per body (`B<tag>`), one node set per fixed support (`S<n>`, all corner and mid-edge nodes on its faces), one material per spec material that a body uses (`M<n>`, n its place in the spec), `*SOLID SECTION` per body, one `*STATIC` step with `*BOUNDARY <set>, 1, 3` per support and one `*DLOAD <element>, P<face>, <Pa>` line per loaded element face. Pressures from several loads on the same element face are added into one line, since the analysis is linear and CalculiX's handling of two lines for one face is not something to rely on. Outputs: `U` to the `.frd`, `S` per element to the `.frd`, and the total reaction of each support set to the `.dat`. Comments name each item's id, name and the entered value beside its SI value, so a reader can trace the deck back to the setup. Set names use positions, not ids, because ids may contain characters CalculiX set names should not.
4. **Determinism.** Numbers are written as Python's shortest round-trip text (`repr`), lines in a fixed order, so the same inputs give the same bytes. `DECK_FORMAT = 1` is written into the deck's first line and changes whenever the text for the same inputs does. Snapshot tests (`worker/tests/test_deck.py`, `worker/tests/snapshots/deck/`) cover a hand-made two-element mesh as C3D10 and C3D4 with the shared spec fixture, and a two-body case in US units with overlapping pressures. A missing snapshot is written only with `CLEARFEA_WRITE_SNAPSHOTS=1`; an existing one is never overwritten by the test.
5. **Refusals.** The generator raises `DeckError` with a plain-language message for anything it cannot translate: no supports, a support or load without faces, a face listed twice, a face or body the mesh does not have, a missing value, a unit of the wrong kind, a Young's modulus of zero or less, a body without a material, and mesh nodes outside every element. M1.12's pre-run list should catch these first; the generator still refuses rather than write a deck that does not match the setup.
6. **Solver options left at CalculiX's defaults** (the default direct solver of the build) until the solver benchmark (M2.11) fixes them.


### ADR-030: The solve job runs CalculiX as a supervised child process, streams its console log with the heartbeats, and reads nodal results from the ASCII `.frd`
2026-10-15 · Accepted (auto-approved under Shubham's standing M1 instruction; reviewed and accepted by Shubham on 2026-10-16)

M1.8 adds runs, the `solve` job, the solver log and the result reader (`worker/clearfea_worker/results/`, physics-critical). Choices it needed:

1. **Runs freeze their inputs from the start.** Migration 0007 adds `runs` (simulation, mesh, the spec as saved when the run started, status `solving` → `succeeded` or `failed`, plain-language problem, result summary, job) and `job_logs`. `POST /api/simulations/:id/runs` needs the simulation's mesh to be ready and made at the saved spec's size, refuses a second run while one solves, and queues a `solve` job whose parameters (`SolveParams`) carry the frozen spec and the mesh id. The worker writes the deck from those two alone, so editing the simulation never reaches a run. Files go under `owners/<owner>/runs/<id>/`: `deck.inp`, `solver.log`, `results.frd`, `results.dat`; the deck and log are uploaded even when the solver stops, so a failed run can be inspected (shown in M1.10). Versions beyond CalculiX's, machine size and cost come with M1.10 and M1.11. Whether the setup is complete is the deck generator's call (`DeckError` becomes a user fault with its message) until M1.12's pre-run list.
2. **CalculiX runs as a child process.** `solver.run_calculix` starts `ccx -i job` in the job's work folder through `stdbuf -oL` (so its output arrives by line rather than in pipe-buffer blocks), passes each line on, keeps the whole output in `solver.log`, and on a cancel from the API terminates it (killed after 5 s). A solver crash ends only the child. A non-zero exit or any `*ERROR` line is a platform fault (`solver_error`, with the first error line), because the deck is generated, not typed. Checked by experiment: CalculiX 2.21 stops with exit status 201 on an input error, but with SPOOLES it solves a model with no supports without any warning and returns nonsense displacements; nothing in M1 can produce that (every support is a fixed face), but the frictionless supports of M2.2 will need their own check for rigid-body motion.
3. **Log streaming through the heartbeats.** `HeartbeatRequest` gains an optional `log` string (at most 65,536 characters): the text written since the previous heartbeat, appended to `job_logs` as one numbered chunk. The worker sends what is queued with each heartbeat (several posts if it must catch up), puts text back if a post fails, flushes the rest before completing, and stops streaming after 1,000,000 characters with one note, since the full log is uploaded as a file. `GET /api/runs/:id/log?after=n` returns the text after chunk n and the n to ask with next; the Run panel polls it with the run every 2 s while the run solves (ARCHITECTURE section 8: polling, no websockets).
4. **Results from the ASCII `.frd`.** The reader takes the last `DISP` and `STRESS` blocks, finds components by their names in the `-5` lines (skipping the derived `ALL` entry), reads node numbers in the short (5-digit) or long (10-digit) format from the block header, joins `-2` continuation lines, and refuses a binary file, a node outside the mesh, a node with no value or the wrong number of values, and non-finite numbers. Values carry the six significant digits CalculiX writes (`E12.5`), enough for display and for the verification tolerances so far. Stresses are CalculiX's nodal values (extrapolated from the integration points and averaged between elements); von Mises is derived from them. Reaction totals come from the `.dat` lines CalculiX writes for each support set (`S<n>` in spec order, now named in one place, `deck.support_set_names`).
5. **Result summary.** A succeeded run stores a `SolveResult`: node count, the largest displacement magnitude and the smallest and largest von Mises stress, each with its node and position, the total reaction of every support, and the CalculiX version, all in SI. The Run panel shows them in the geometry's length unit, MPa and N (fixed until M2.1), numbers only. Field files for the viewer are M1.9.
6. **Checked with the solver.** `worker/spikes/solve_check/` runs these steps on the M1.7 bar: uniform compression with Poisson's ratio 0 (σxx = −p at every node, other components zero, von Mises p, tip displacement p·L/E, reaction p·A), Poisson's ratio 0.3 (mid-length stress p, largest von Mises at the clamp) and a cantilever under pressure (tip deflection within 1 percent of Timoshenko beam theory; reaction equal to the load less the part on held nodes, as M1.7 found). 10 of 10 checks pass. It stands in until V-01, V-02 and `make verify` (M1.13).

Not done here: a heartbeat-timeout sweep for jobs whose worker died (a run whose worker is lost stays `solving`, and blocks the next run of that simulation), a time limit on the solver, and the solver's thread count and memory limit per machine size (M1.11, M2.11).

### ADR-032: A run records the versions that produced it and the files its job stored; the deck and log are served as plain text to view or download

M1.10 completes the run record (ARCHITECTURE section 4: spec, mesh, deck, versions) and makes the solver input and log viewable and downloadable (DECISIONS "Solver input"). Choices it needed:

The package version alone stays `0.0.0` until releases exist.
3. **The run stores its own copy of the versions** (`runs.software`, `RunSoftware`): Gmsh and OpenCASCADE from the mesh's own job when the run is created, then ClearFEA, deck format and CalculiX from the solving worker when its job ends, succeeded or failed. Gmsh is the mesh's version, not the solving worker's, because the mesh is what Gmsh made. Runs from before M1.10 show every version as not recorded; `SolveResult.software.calculix` stays for them.
4. **The mesh is referenced, not copied.** `RunView.mesh` (size, order, node and element counts) is read from the run's mesh row, which does not change once ready and cannot be deleted while a run uses it (`ON DELETE RESTRICT`). The mesh itself is downloadable as part of the deck, which lists every node and element in CalculiX's own format; a separate mesh export is M3.8.
5. **The frozen spec is shown, and a changed setup is pointed out.** `RunView.spec` is the setup as saved when the run started. The Run panel compares it with the current setup by content (key order ignored) and says when they differ, so results are never read as belonging to an edited setup.
6. **The run lists its stored files.** When the solve job ends, the API checks which of the run's six files exist and stores their names (`runs.files`). A run the solver stopped on keeps its deck and log; a run that stopped before the solver started (for example a setup the deck generator refuses) has neither, and says so.
7. **Deck and log are served as plain text.** `GET /api/runs/:id/files/deck.inp` and `/solver.log` answer `text/plain; charset=utf-8` with `nosniff` and a `sandbox` content security policy, because the deck carries names the user typed; `?download=1` makes it an attachment named `clearfea-run-<first 8 of id>-<file>`. Other run files are not served here. The Run panel links to both (view opens a new tab), so the browser streams large decks itself instead of the app holding them in memory. While the run solves, the live log stays in the panel; the stored files appear when it has finished (409 before, 404 for another user's run).

### ADR-033: Jobs are metered by the worker's handler time, billed per started second at the rate fixed when queued, and charged in whole micro-credits in the same batch that completes them
2026-10-15 · Accepted (auto-approved under Shubham's standing M1 instruction; reviewed and accepted by Shubham on 2026-10-16). ADR-085 settles item 6: a cancelled job is charged the time it used.

M1.11 adds metering and the ledger (ARCHITECTURE section 6, "Metering"; DECISIONS "Unit of charge" and "Phase 0 wallet"). Choices it needed:

1. **The billable phase is the job's handler.** The worker measures wall-clock time with a monotonic clock from the start to the end of the job's handler, which covers its downloads, the meshing or solving, and its uploads: the time the job occupies the machine. Claiming, queue time and the worker's start-up are outside it. Every completion carries `metering.billableMs` (whole milliseconds, rounded up; `Metering` in `jobs.schema.json`), and the API refuses a completion without it. CPU seconds and peak memory are not recorded yet; the solver benchmark (M2.11) and the estimator (M2.12) add them when they need them.
2. **Only mesh and solve jobs are charged.** Import is free (DECISIONS "Where compute runs"); noop and report are not metered. Every job still records its measured time (`jobs.billable_ms`).
3. **Per-second billing rounds up.** Billed seconds are the measured time rounded up to whole seconds; cost is billed seconds × hourly rate ÷ 3600, rounded to the nearest micro-credit (halves up), in integer arithmetic (`apps/api/src/billing/cost.ts`).
4. **Money is whole micro-credits.** Play money is counted in credits (DECISIONS speaks of a credit grant) and stored as integers of one millionth of a credit, so sums are exact and the ledger reconciles to the unit. The web app shows credits with up to six decimals. What a credit is worth in real money is decided with real payments, after the beta.
5. **Machine sizes are a configuration table.** Migration 0009 adds `machine_sizes` (name, rate in micro-credits per hour, one default) with one row, `local`, at a placeholder 1 credit per hour until beta cost data sets real rates. A metered job takes the default size and copies its rate when it is queued, so a later rate change applies only to new jobs. Thread count and memory limits per size come with the estimator and machine-size choice (M2.12).
6. **Who pays follows the failure classification.** A succeeded job and a job that failed through the user's setup (`user_fault`) are charged; a fault in ClearFEA (`platform_fault`, including a success the API turns into one because outputs are missing) is not, though its time is recorded. Cancelled jobs report nothing yet, so they are not charged; the cancel button and stop limit (M8.2) settle that.
7. **The ledger is append-only and written with the completion.** `ledger_entries` holds the owner, the amount (a charge is negative), the owner's running balance after the entry, the reason (the job type) and the job, which is unique, so a job is charged at most once. The charge is inserted only while the worker still holds the job, in the same D1 batch as the update that completes it, so a job is completed and charged together or not at all. Nothing updates or deletes an entry. Balances start at 0 and may go below it: credit grants, the wallet page and refusing runs on a low balance come with the estimate (M2.12) and the wallet (M8.1).
8. **The run shows its machine and cost.** `RunView.machine` (size and rate, from the solve job) and `RunView.cost` (billed seconds, amount, whether charged; null while solving) are read from the run's job, whose metering columns are written once when it ends. The Run panel's run record shows both; runs from before M1.11 say they were not metered. The mesh job's charge is in the ledger but not shown in the Mesh panel until the wallet page (M8.1).

### ADR-034: Pre-run validation is one pure function in `packages/spec`, enforced by the API before a job is queued and shown as a list under the Run button

M1.12 adds pre-run validation (ARCHITECTURE section 8; DECISIONS "Pre-run checks"). Choices it needed:

1. **One function, two callers.** `preRunProblems(spec, topology)` in `packages/spec/src/prerun.ts` returns what stops a saved setup from running, each as a `SpecProblem` (the item it belongs to and a plain-language message that names the item and says what to do). ### ADR-039: Prescribed displacement and frictionless support as per-node constraints; rigid-body check; reactions shared per node
2026-10-15 · Accepted (under Shubham's standing M2 instruction; reviewed and accepted by Shubham on 2026-10-16)

M2.2 adds the prescribed displacement and the frictionless (symmetry) support (DECISIONS product table, planar faces only). Choices it needed:

1. **Spec shape.** Two new support types join `supports` (ADR-026 item 1; the spec stays version 1, since adding an item type changes no existing data): `displacement` with `x`, `y`, `z`, each a length quantity, `"free"`, or null until chosen, in global axes; and `frictionless` with faces only. One frictionless type serves both names: for a solid in linear statics a symmetry plane and a frictionless support are the same condition (no motion along the normal, free in the plane). It is bilateral: the face does not lift off. A new prescribed displacement starts with every component free, so the user gives a value only to what it holds.
2. **Every support becomes per-node constraints.** At each node of its faces a support says u·d = v for some unit directions d: fixed x, y, z = 0; prescribed displacement each component that is not free; frictionless the face's normal = 0. `deck/constraints.py` reduces a node's constraints to an orthonormal set of held directions with the displacement along each, and refuses supports that ask a node for different motions (a moved face next to a fixed one, a move along a symmetry plane's normal) with both names and the node's position. The normal of a frictionless face comes from the mesh (summed element-face area vectors), the face must be flat to 1e-6 of its size, and a normal within 1e-9 of an axis is taken as that axis. Saving already refuses a frictionless face whose topology type is not `plane`.
3. **Deck layout.** A setup with fixed supports only is written exactly as before (ADR-029; the snapshots are unchanged). Otherwise each support still gets its node set `S<n>` and comment (components with their entered and SI values, normals per face), and the held nodes not on a fixed support are written in groups `C<k>` of identical holds: on global axes as `*BOUNDARY` on those degrees of freedom with their values, or, for a node held along a direction that is not an axis, with a `*TRANSFORM, TYPE=R` on its group whose first axes are the held directions. A node held in all three directions is written in global axes. Each node is in at most one group, so no node gets two transforms (a node on the edge of two leaning symmetry planes is held along both normals by one transform). Checked with CalculiX 2.21: nonzero `*BOUNDARY` values in a step, repeated equal holds on a node, and that `*NODE FILE` and `TOTALS=ONLY` report global values for transformed nodes while a per-node `*NODE PRINT` needs `GLOBAL=YES`.
4. **Rigid-body check.** CalculiX solves a model the supports do not hold without a warning (ADR-030 item 2). Before writing a deck, the generator forms the 6 × 6 matrix of all held directions against the rigid-body motions (translation and rotation about the model's centre, scaled by its size) and refuses the setup if any motion has an eigenvalue below 1e-10 of the largest, naming the free motions in words ("it can still slide along x"). The refusal is the user's fault (ADR-033: the second of machine time is charged). Pre-run validation cannot do this without face normals, so the API still lets such a setup queue; a topology-level check is left for later.
5. **Reactions are shared per node.** Supports meet at edges, so summing CalculiX's reaction per support node set counts edge nodes twice. With any support other than fixed, the deck prints the reaction force of every held node (`RALL`, global axes), and the result reader gives each support the part of a node's force along its own held directions: the force is projected onto the node's held directions and written with the least-squares coefficients, so supports holding different directions get exactly their components and two holding the same direction share it equally. The projection also drops the part of CalculiX's nodal force that is applied load along a free direction (a pulled end's corner on a symmetry plane), which is not a reaction. Fixed-only setups keep the M1 totals, so two fixed supports sharing an edge still count it in both; changing that changes the two-body snapshot and is left for M3.2's balance check.
6. **No load needed when something is moved.** ADR-034 item 3 is narrowed: a setup with no load runs when a prescribed displacement has a component other than zero; the Loads group is then complete too.
7. **Verification.** V-09 is a quarter of V-01's tube between symmetry planes at 30° and 120° (so the deck needs local axes) on a frictionless base, checked against the full tube's Lamé values and the hoop force p·a·L on each cut plane. V-24 (new) is a quarter bar on two symmetry planes stretched by prescribed end displacements, checked to 0.1 percent. The harness gains reaction checks per support and measures the balance of a load-free case against the sum of the reactions' sizes. V-01 stays a fixed-end case; the coverage matrix now lists V-09 and V-24 for frictionless supports. `worker/spikes/support_check/` checks every node and the refusals by hand.


### ADR-040: Force as a uniform traction, gravity and centrifugal load as CalculiX body loads, applied loads taken out of reactions
2026-10-15 · Accepted (under Shubham's standing M2 instruction; reviewed and accepted by Shubham on 2026-10-16)

M2.3 adds the force on a face, gravity and the centrifugal load (DECISIONS product table). Choices it needed:

1. **Spec shape.** Three load types join `loads` (the spec stays version 1, ADR-026 item 1). `force`: faces and `x`, `y`, `z`, each a force quantity or null, in global axes. `gravity`: `x`, `y`, `z` accelerations, no faces; it acts on every body, and gravity downwards is entered as, for example, z = −1 g, since the model's "up" is the user's to say. `centrifugal`: `angularVelocity`, `axisPoint` (three lengths) and `axisDirection` (three plain numbers of any length but zero), no faces; the sense of rotation does not matter in a static analysis. A material gains an optional `density` (a density quantity), needed only when a gravity or centrifugal load exists; it is optional in the schema so stored specs stay valid, and pre-run validation asks for it. Values start empty: no default "down" or axis is guessed.
2. **A force is a uniform traction.** The entered force is spread over its faces in proportion to area, t = F / A over all its faces, and written as consistent nodal loads (`*CLOAD`): each node gets F times the integral of its shape function over the element faces, divided by the total area (a seven-point rule on six-node triangles, exact on flat ones; corners of a flat six-node triangle get nothing, mid-edge nodes a third). The shares add up to one, so the nodal loads sum to the entered force; components below 1e-12 of the largest are rounding and are written as zero. Several forces on one node add up. A remote force with a moment, applied through a reference point, is M2.4.
3. **Gravity and centrifugal load are CalculiX's own body loads.** Each body's element set gets `*DLOAD` `GRAV` (size and unit direction of all gravity loads added up) and `CENTRIF` (ω², a point on the axis, the unit axis), and each material with a density gets `*DENSITY`. CalculiX allows one centrifugal load per element set, so a setup has at most one; a second is refused by saving and by the deck generator. Checked with CalculiX 2.21: the field order of both lines, that the centrifugal force is ρω²r with r the distance vector from the axis, and that two `*DLOAD` cards in one step add up.
4. **Applied loads are taken out of reactions.** CalculiX's RF at a held node is the reaction plus the load applied at that node (manual section 6.11.5), so a column's base reaction under its own weight was short by the weight of the base layer, and a force on a face touching a support was partly missing from that support's reaction. The result reader now subtracts, at every held node, the force loads exactly as the deck writes them and the body loads computed the way CalculiX integrates them (C3D4: one point; C3D10: CalculiX's four-point rule, which matters on curved elements); for fixed-only setups it subtracts the sum over each support's nodes from CalculiX's total. Checked against CalculiX's own nodal loads on a curved ring to its printed digits, and by equilibrium in `worker/spikes/load_check`. Pressure on held nodes is not taken out yet (ADR-029; M3.2's balance check), and two fixed supports sharing an edge still count it twice (ADR-039 item 5).
5. **Setup.** The Loads group offers "Add a pressure", "Add a force", "Add gravity" and "Add a centrifugal load". A force takes the faces selected in the viewer, like a pressure; gravity and a centrifugal load show no faces. The material panel has a density field; with a body load present, a material without a density is marked incomplete and the run is refused with that reason.
6. **Verification.** V-10 (column standing on a fixed base under its own weight, in inches with lb/in³ and g) checks the base reaction against the weight, the mid-height stress ρgh/2 and the top's shortening. V-06 (a quarter of a thin ring on three symmetry planes at 10,000 rpm) checks the hoop stress and radial growth on both faces against the plane stress rotating disc, and each cut's reaction against the hoop force ρω²t(b³ − a³)/3. V-02's end load becomes a force on the patch, as VERIFICATION.md planned; its results do not change, and it gains a check of the clamp's reaction. The harness adds forces and body loads (from the volume and first moment the run's surface encloses) to the applied total it balances reactions against.

### ADR-041: Remote force and moment as the statically equivalent linear traction on the faces, written as nodal loads
2026-10-15 · Accepted (under Shubham's standing M2 instruction; reviewed and accepted by Shubham on 2026-10-16)

M2.4 adds the remote force and moment (DECISIONS product table). Choices it needed:

1. **Spec shape.** One load type, `remote`: faces, `point` (three lengths, the reference point), `force` (three force quantities) and `moment` (three moment quantities), all in global axes, the moment right-handed; every value starts empty and pre-run validation asks for all nine (0 for a component it does not have), like a force. The spec stays version 1 (ADR-026 item 1). A force alone at a point, or a moment alone, is the same load with the other part zero, so there is no separate "remote force" and "moment" type.
2. **Distributing, not rigid.** The faces stay free to deform: the load is carried to them as the linear traction t(x) = F/A + α × (x − c) with A the faces' area, c their centroid and J α = M + (P − c) × F, J the faces' polar second moment of area about c. That is the evenly spread traction that has the force F and, about P, the moment M; it is what a distributing coupling with weights by area applies (the usual default for a remote load, since it adds no stiffness). A rigid (kinematic) connection, which keeps the faces' shape, is not offered at the gate; it is in "Parked ideas" for the maintainer to decide.
3. **Nodal loads, no reference node.** The traction is written as consistent nodal loads (`*CLOAD`), integrated with the force's seven-point rule (ADR-040 item 2). Because the rule's points sit where the shape functions put them, the nodal loads add up to F and have the moment M about P to rounding (checked to 1e-12 on curved faces in the worker tests). The deck needs no reference node with rotational degrees of freedom and no `*COUPLING`/`*DISTRIBUTING`, whose moment handling would have to be trusted from the solver; ARCHITECTURE section 7 planned the coupling and now records this instead. The result reader takes remote loads on held nodes out of the reactions with the force loads (ADR-040 item 4). The run's result still reports reaction forces only; reaction moments per support come with M3.2.
4. **Setup.** The Loads group gains "Add a remote force and moment"; the panel takes the faces selected in the viewer and has three groups of x, y, z fields: reference point, force at the point, moment at the point. The reference point is not drawn in the viewer yet.
5. **Verification.** V-04 (a round stub clamped at one end, an axial force through a point 10 mm off its axis plus a torque and a bending moment, in cm, kN, lbf, N·m and lbf·in) checks von Mises on top, underneath and on the side along the middle against Saint-Venant extension, bending and torsion, which together pin the force, the moment and the point's lever, and the clamp's reaction against the force. `worker/spikes/load_check` solves a column loaded through a point off to the side and above it and checks, node by node, that the base reaction balances the force and, about the point, the moment, and that the axial stress at mid-height follows beam theory.

### ADR-042: Hydrostatic pressure from a fluid density, gravity and a free-surface point, written as nodal loads
2026-10-15 · Accepted (under Shubham's standing M2 instruction; reviewed and accepted by Shubham on 2026-10-16)

M2.5 adds hydrostatic pressure (DECISIONS product table; PLAN: fluid density, free-surface level, direction). Choices it needed:

1. **Spec shape.** One load type, `hydrostatic`: faces, `fluidDensity` (a density), `gravity` (three accelerations in global axes, as the gravity load takes them) and `freeSurface` (three lengths, any point on the free surface). Gravity gives both the direction of depth and its size, so the pressure is p(x) = ρ g · (x − s) where that is positive and zero above the surface: a level is the free-surface point's height along gravity, and the surface may lean, for example in an accelerating tank. Gravity on the fluid is not applied to the bodies; their weight is a separate gravity load. Every value starts empty; pre-run validation asks for all of them, refuses a density that is not positive and gravity that is zero. The spec stays version 1 (ADR-026 item 1).
2. **Fluid outside, pressing in.** The fluid is on the outside of every face, so the pressure pushes on the face towards the body, like a positive pressure (ADR-026 item 4). A fluid inside a closed cavity, such as a tank's own wall seen from inside, is the same thing: the wet faces' outside is the cavity.
3. **Nodal loads, not `*DLOAD`.** ARCHITECTURE section 7 planned a pressure per element face as `*DLOAD`; that would make the pressure constant on each element face (a staircase) and, like a uniform pressure, leave the part landing on held nodes in the reactions (ADR-029). Instead the traction p n is written as consistent nodal loads (`*CLOAD`) with the seven-point rule of a force on faces (ADR-040 item 2), which is exact on flat element faces below the surface, and the result reader takes the part on held nodes out of the reactions with the other nodal loads (ADR-040 item 4). An element face the free surface crosses is split into four, and its pieces again where the surface crosses them, six levels deep, so the kink at the surface is followed to a few parts in a million of the load. A load whose faces are all above the free surface is refused by the deck generator with a message to check the point and the direction of gravity.
4. **Setup.** The Loads group gains "Add a hydrostatic pressure"; the panel takes the faces selected in the viewer and has the fluid density, gravity on the fluid (x, y, z) and a point on the free surface (x, y, z). The free surface is not drawn in the viewer.
5. **Verification.** V-05 (a strip of tank wall clamped at its base, water up to 100 mm below its top, ν = 0 so it is a cantilever beam; in GPa, g/cm³, ft/s², g, m/s², in, m and cm) checks the base reaction against ρ g b H²/2, the bending stress at two heights against the cubic moment ρ g b (H − z)³/6 and the top deflection. The harness's balance check integrates the pressure exactly over each surface triangle's wet part. `worker/spikes/load_check` checks a sunk column (nodal loads equal Archimedes' buoyancy with no moment, and the base reaction balances them although the held base is wet) and a column wet on one side.

### ADR-043: Elastic support as normal-only grounded springs per node, its reaction from displacements
2026-10-15 · Accepted (under Shubham's standing M2 instruction; reviewed and accepted by Shubham on 2026-10-16)

M2.6 adds the elastic support (DECISIONS product table: "elastic (spring) support"; ARCHITECTURE section 7: grounded springs per node weighted by nodal area). Choices it needed:

1. **Normal only.** The support is a Winkler foundation: it pushes back along each face's normal with the pressure k (u · n), k the foundation stiffness (pressure per unit of displacement, `foundationStiffness` in `units.json`, ADR-038), both ways (it does not lift off), and does not resist sliding along the face. This is what "foundation stiffness" means in common FEA tools. A part held only by an elastic support on one flat face can still slide, so the deck generator's rigid-body check (ADR-039) counts each spring as resisting motion along its direction and refuses such a setup by name; the panel's hint says the part may need other supports. A tangential stiffness would be a separate, later option.
2. **Spec shape.** Support type `elastic`: faces and `stiffness` (a foundationStiffness quantity, null until entered, greater than zero). Pre-run validation asks for faces and the stiffness. The spec stays version 1 (ADR-026 item 1).
3. **Lumped springs per node and face.** The foundation's stiffness k ∫ N_i N_j n nᵀ dA is lumped by rows: node i of a face gets one spring along d_i = ∫ N_i n dA / |…| with stiffness k ∫ N_i dA, integrated with the seven-point rule of a force on faces (ADR-040). The shares add up to the area, so a uniform pressure moves a flat face by exactly p/k on any mesh (the springs' forces are the pressure's consistent nodal loads). A node on two faces of one support gets a spring for each. Flat six-node triangles' corners get none, as they get no share of a force; a share at or below 1e-12 of the largest (or negative, at curved corners) gets no spring.
4. **SPRING1 with an orientation, not SPRINGA to a held node.** Each spring is a `SPRING1` element at the node, acting along local direction 1 of an `*ORIENTATION` whose x axis is d_i (or along the global degree of freedom when d_i is an axis). The first version used `SPRINGA` elements to a held far node; the support check found that CalculiX counts a `SPRINGA` in the average of nodal stresses with zero stress (ccx 2.21 `extrapolate.f`), which halved the stress at those nodes (V-25's outside read 27 percent low), and that it works out a `SPRINGA`'s force for RF from deformed positions. `SPRING1` elements are left out of the average, need no extra nodes and are linear. The springs add k d dᵀ in global axes, so they work at nodes that frictionless supports hold through `*TRANSFORM` (ADR-039).
5. **Reaction from displacements.** The deck prints the displacement of each elastic support's nodes (`*NODE PRINT, NSET=S<k>, GLOBAL=YES`, `U`, seven digits), and the result reader recomputes the springs from the spec and mesh and sums −k_i d_i (d_i · u_i), the force CalculiX's linear `SPRING1` applies. Other supports' reactions are unchanged; a spring at a node another support holds is part of the solved system, so that node's RF is still that support's reaction. Decks without an elastic support are byte-identical to M2.5 (snapshots unchanged).
6. **Setup.** The Supports group gains "Add an elastic support"; the panel takes the selected faces and the foundation stiffness (N/mm³, N/m³, MN/m³ or lbf/in³). Springs are not drawn in the viewer.
7. **Verification.** V-07 (a 100 × 60 × 40 mm block on a foundation of 2,000 lbf/in³ with two symmetry planes, pressed by 6 kN) checks settlement F/(kA), top displacement, uniform stress and the foundation reaction to 0.1 percent; new V-25 (V-09's quarter tube in a stiff sleeve, k = 5 × 10¹¹ N/m³) checks the curved case against Lamé with σr(b) = −k u(b), including springs at nodes held through local axes. `worker/spikes/support_check` adds a turned bar pressed into a foundation on a leaning face (every node's displacement and stress exact, the support's reaction p·A along the normal) and the refusal of an elastic support alone on one face.

### ADR-044: Uniform temperature change as initial and final nodal temperatures, expansion per material
2026-10-15 · Accepted (under Shubham's standing M2 instruction; reviewed and accepted by Shubham on 2026-10-16)

M2.7 adds the uniform temperature change (DECISIONS product table; ARCHITECTURE section 7: initial and final temperature fields). Choices it needed:

1. **Spec shape.** One load type, `temperature`, with `change` (a `temperatureDifference` quantity, so 90 °F is 50 K with no offset; ADR-038), positive for warming. It has no faces: every body changes by the same amount. One per setup, like the centrifugal load: a second is refused by the spec check and the deck generator, since two would only add up and one value is clearer. Materials gain an optional `thermalExpansion` (a `thermalExpansion` quantity, the coefficient of linear expansion, any sign, zero allowed), asked for by pre-run validation and the material's mark only when the setup has a temperature change, as density is for body loads (ADR-040). The spec stays version 1 (ADR-026 item 1).
2. **The change is from the stress-free state; no absolute temperature.** With a constant coefficient, CalculiX's thermal strain α (T − T_initial) depends only on the change, so the setup asks for nothing else. The deck starts every node at 0 (`*INITIAL CONDITIONS, TYPE=TEMPERATURE`, `NALL, 0.0`), ends the step at the change (`*TEMPERATURE`, `NALL, ΔT` in kelvin) and gives each used material `*EXPANSION` in 1/K without a `ZERO` reference (checked with ccx 2.21: a held unit cube gave −Eα ΔT exactly). The zero is only a datum: temperature-dependent properties (M5.5) and thermal stress (M5.4) will need absolute temperatures and will add a reference temperature then. `*EXPANSION` and the temperature lines are written only when a temperature change exists, so every other deck is byte-identical (snapshots unchanged; new snapshot `thermal-two-bodies-c3d10`).
3. **Reactions.** A temperature change applies no nodal load, so reactions need no correction (ADR-040 item 4) and must balance each other; the verification harness counts it as no applied load and measures the balance against the reactions' sizes, as for a prescribed displacement (ADR-039). Pre-run validation counts it as a load.
4. **Setup.** The Loads group gains "Add a temperature change"; its panel has one field, Change (°C, K or °F), with a hint that negative means cooling. The material panel gains Thermal expansion (1/K, 1/°C, 1/°F, µm/(m·K), µin/(in·°F)). The temperature is not drawn in the viewer.
5. **Verification.** V-08 (a 200 × 20 × 10 mm bar between frictionless ends with two symmetry planes, warmed by 90 °F, steel in ksi and µin/(in·°F)) checks von Mises EαΔT, both end reactions ±EαΔT·A, which show the compression's sign, and the sideways growth (1 + ν)αΔT to 0.1 percent. `worker/spikes/load_check` adds a bar warmed freely on three planes (every node moves αΔT·x, no stress, no reaction) and the same bar held at both ends (−EαΔT along x and nothing else at every node, the end reactions, the sideways growth).

### ADR-045: Local mesh sizes as Gmsh distance fields growing at 20 percent, a free element order, and a quality summary per mesh
2026-10-15 · Accepted (under Shubham's standing M2 instruction; reviewed and accepted by Shubham on 2026-10-15 in the M2.8 thread)

M2.8 adds local mesh sizes on faces, edges and bodies, the element order choice and the mesh quality summary (DECISIONS product table, "Meshing"). Choices it needed:

1. **Spec shape.** `mesh` gains `order` (1 or 2) and `local`, a list of items `{ id, name, scope, tags, size }` where `scope` is `faces`, `edges` or `bodies`, `tags` are topology.json tags and `size` a length. Both are optional so specs saved before M2.8 stay valid: no order means 2 and no list means none (the spec stays version 1, ADR-026 item 1; new specs get both). Local sizes only refine: one larger than the global size is an error in the setup tree and is refused by the worker, rather than silently doing nothing. Local sizes are tree items under Mesh, with the same complete / incomplete / error marks as loads; ids are unique across materials, supports, loads and local sizes.
2. **Gmsh fields, smallest wins.** A face or edge gets a `Distance` field (sampled at about two points per local element over the entity, between 20 and 400) and a `Threshold` on it: the local size on the entity, growing linearly by 0.2 per unit of distance up to the global size, so neighbouring elements differ by about 20 percent and the zone ends (global − local)/0.2 away. A body gets a `Constant` field of its size inside it and on its boundary. A `Min` of them is the background mesh; `Mesh.MeshSizeMax` stays the global size. Without local sizes no field is set, so meshes with only a global size are the M1.6 ones (no deck or verification result changed). Checked on the test block: the elements along a 1 mm local face or edge have a mean edge of 0.8 to 1.4 mm while the far end keeps its 8 mm.
3. **Edges in topology.json.** The import job now lists every edge (`edges`: tag, length, box, the faces it bounds, and a polyline of points for the viewer, sampled from the curve's own parametrisation: 2 points for a line, 49 for a curve; zero-length degenerate edges are left out). Points are part of topology.json rather than a new display file, so the viewer gets them with the face data it already loads; the mesh job's identity check compares edge lengths, boxes and faces (not points) at the same 1e-9 tolerance as faces (ADR-023 item 4), and an edge that differs fails the job as a platform fault. Geometries imported before M2.8 have no `edges`; their setup says to upload the file again to size edges.
4. **Picking edges.** While a local size on edges is open, the viewer draws the geometry's edges over its faces and a click picks the edge whose segment passes nearest the pointer on screen, within 8 pixels, ignoring edges behind the surface under the pointer. Edges have their own selection; faces keep theirs. A local size on bodies is a list of checkboxes (a single-body geometry's body is ticked when it is added), and opening it selects the bodies' faces in the viewer.
5. **Element count guard.** The pre-mesh estimate (ADR-028 item 5) adds each local size's zone on the high side: a face's parallel set on the body side (area, half tube along its perimeter, half sphere at corners), an edge's tube with round ends, a body filled at its size, integrated over the graded size. On the test block it is 1.3 to 4.5 times the actual count. After meshing, more than 2,000,000 elements is refused as the user's fault too.
6. **Element order.** First-order (four-node, C3D4) meshes are offered with a hint that they are too stiff in bending; second order stays the default. The deck generator, loads and result reader already handled C3D4 (ADR-029); V-26 checks it end to end.
7. **Quality summary.** Every mesh reports Gmsh's `gamma` for each element (inscribed to circumscribed radius ratio, 1 for a regular tetrahedron): its lowest and mean value and a ten-bin histogram, and the smallest scaled Jacobian (`minSJ`, below 1 only for curved second-order elements). It is stored with the mesh (migration 0010) and shown under the mesh's counts as numbers only, without a verdict.
8. **What makes a mesh current.** A mesh records the local sizes it was made with (complete ones only, tags sorted, sizes as entered); a mesh is current when the global size, order and those local sizes equal the spec's (`sameMeshSettings` in `packages/spec`, used by the API before a run and by the web app). Names do not count. Meshing with an unfinished local size is refused with its name, so nothing is left out unseen. M2.10 turns the same settings into the reuse hash.
9. **Verification.** V-03, a plate with a hole (d/W = 0.1, ν = 0) on three symmetry planes with a 0.5 mm local size on the hole (0.25 mm full tier) against a 5 mm global size, checks the peak stress against Ktg = 3.025 (Howland; Peterson's fit) and the far-field stress. V-26 is V-24's kind of bar under a force with four-node tetrahedra, exact to 0.1 percent.

### ADR-046: A material library of 24 metals copied as printed from MIL-HDBK-5G, and users' own materials kept per user
2026-10-15 · Accepted (under Shubham's standing M2 instruction; reviewed and accepted by Shubham on 2026-10-16)

M2.9 adds the generic material library and custom materials saved per user (DECISIONS product table, "Materials"). Choices it needed:

1. **One public-domain source.** Every library value comes from MIL-HDBK-5G, *Metallic Materials and Elements for Aerospace Vehicle Structures* (U.S. Department of Defense, 1 November 1994), Distribution Statement A: approved for public release, distribution unlimited (scans at archive.org, DTIC ADA295150 and ADA322636). A U.S. government handbook can be copied into an AGPL repository, unlike ASM, MMPDS or design-code tables (non-goal 9, CLAUDE.md). Only the typical physical constants are taken (E, μ, ω and α); none of the handbook's strength allowables, which would be design data and are not needed before M3.5's yield strength.
2. **Which materials.** 24 common structural metals, within DECISIONS' 20 to 30: carbon steel 1025, low-alloy steel (4130 family), annealed austenitic stainless (301/302/304/321/347), 17-4PH and 15-5PH; aluminium alloys 2014, 2024, 2219, 5052, 5083, 5086, 6061, 7050, 7075 and castings 356.0 and A356.0; magnesium AZ31B; Ti-6Al-4V; A-286, Hastelloy X, Inconel 600, 625 and 718; copper beryllium C17200. Tables that leave Poisson's ratio blank (commercially pure titanium, C86300 bronze) are left out rather than filled from elsewhere. Non-metals (cast iron, polymers, concrete) need another citable public-domain source and are parked.
3. **Values as printed, in the source's units.** Each material holds its values exactly as the table prints them, as quantities in the table's units (E 9.9 × 10³ ksi is stored as 9900 ksi, ω as lb/in³, α as µin/(in·°F)), so a reviewer can check every number against the cited table and the only conversion is the units table's (ADR-038). A material's `source` names the table, page and product form; where a table gives a value per temper (17-4PH density) the source says which was taken. Thermal expansion is filled only where the table prints a number (5086, 7050: mean from 68 to 212 °F); where it refers to a curve, it is left empty rather than read off a figure, and pre-run validation already asks for it when a setup has a temperature change (ADR-044). The panel says the values are generic, not minimum or design values.
4. **The library is a reviewed file, not database rows.** `packages/spec/library/materials.json` (shape `MaterialLibrary` in `simulation.schema.json`) is loaded and checked when `packages/spec` is first imported: unique ids starting `lib-` and names, complete E, μ and density, a source, units of the right kind. A spec test also checks every value converts to the range of engineering metals, which catches a unit or decimal slip. ARCHITECTURE section 4 planned library rows with no owner in the `materials` table; a file keeps the values under code review and in git history, and the API serves it as is. This changes no product behaviour.
5. **Library and custom materials are `IsotropicMaterial`s.** The same schema definition as a spec's material, with an optional `source` text, so there is no second definition of a material. `GET /api/materials` returns `{ library, custom }`; `POST /api/materials` saves a copy of a spec material for the signed-in user under a new id (Young's modulus and Poisson's ratio required, a name they already use refused with 409); `DELETE /api/materials/:id` removes one of theirs. Migration 0011 adds `materials` (owner, name unique per owner, the material as JSON). Custom materials belong to the user, not a project, so they are reusable across projects. Editing a saved material in place is not offered: add it, change it, save it under a new name.
6. **Copied, never referenced.** Adding a library or saved material copies it into the spec under a new item id (ADR-026 item 5), so deleting or changing a saved material, or a later library update, never changes a simulation or a run. The copy keeps its `source`; changing any of its values drops the source, since the values no longer match it, while renaming keeps it. The deck generator ignores `source`.
7. **Setup.** The Materials panel has "Add an empty material" and below it a material list (your materials first, then the library) showing the chosen material's values in the project's units with the values as given, and its source; "Add this material" copies it, and a saved material can be deleted there. A material's panel shows "Values from …" and has "Save to my materials".

### ADR-047: Meshes reused by a SHA-256 settings hash of geometry, scaling and mesh settings, shared across a user's simulations
2026-10-15 · Accepted (under Shubham's standing M2 instruction; reviewed and accepted by Shubham on 2026-10-16)

M2.10 makes meshes reusable across runs when the mesh settings are unchanged (DECISIONS data structure). Choices it needed:

1. **What the hash covers.** Everything that decides a mesh and nothing else: the geometry id, the scaling it is imported at (its confirmed unit), the global size, the element order and the complete local sizes (scope, sorted tags, size), each size as entered. It is SHA-256 in hex of `meshSettingsText` in `packages/spec`, which writes these in a fixed key order with a settings version (`MESH_SETTINGS_VERSION`, 1) that a future mesher change can bump so older meshes stop matching. The same settings decide `sameMeshSettings` (ADR-045 item 8), so a reused mesh is always current for the spec. A size typed in another unit (0.4 cm against 4 mm) is another mesh, as ADR-045 decided: equal after conversion is not the same as equal as entered, and an extra mesh is cheaper than a reuse that differs by rounding. Local sizes keep their setup order; names and ids do not count.
2. **Gmsh and OpenCASCADE versions are not in the hash.** The API does not know the worker's versions before a job runs, and they are pinned; a bump is its own pull request (CLAUDE.md), which bumps `MESH_SETTINGS_VERSION` if meshes change. A run still records the Gmsh and OpenCASCADE versions of the mesh it actually used (ADR-032).
3. **Where reuse happens.** In `POST /api/simulations/:id/mesh`: after the existing checks (size entered, local sizes finished, unit confirmed, this simulation's mesh not still being made), the user's newest mesh with that hash that is ready, or failing that still being made, becomes the simulation's mesh (`simulations.mesh_id`). The answer is 200 with `reused: true` and no job is queued, so nothing is charged; a new mesh is 201 with `reused: false`. Runs keep using the simulation's current mesh as before, so every run on unchanged settings already shares one mesh, and changing the settings back picks the earlier mesh again at once. The run route does not swap meshes on its own: the setup shows which mesh a run will use.
4. **Scope of sharing.** Reuse is per user (every query is owner-scoped) and across that user's simulations of the same geometry, since a mesh depends on nothing in the setup but its mesh settings. Meshes are immutable once ready, and a run references its mesh by id, so sharing never changes a run. Another user with the same file never shares a mesh: their geometries are separate records.
5. **Failed meshes are never reused**, so asking again retries a mesh that failed for whatever reason. A mesh still being made is reused, and the simulations that share it see it become ready or fail together.
6. **Storage.** Migration 0012 adds `meshes.settings_hash` and an index on (owner, hash). Meshes made before M2.10 have no hash and are never reused; there is no backfill, since D1 has no SHA-256 in SQL and those are local development meshes. Two requests with the same new settings at the same instant can still both make a mesh; the newest ready one wins later reuse. That race costs one extra mesh job and nothing else, so no lock is added.
7. **Setup.** The Mesh panel says when its mesh was reused: "Reused the mesh made earlier with these settings. Nothing was meshed or charged again." (or, for a mesh another simulation is still making, that this simulation will use it).

2. **SPOOLES stays the solver for every run.** It meets the verification tolerances: `make verify` passes with it, and with every deck forced onto an iterative solver it does not (item 4). Slender parts need less.
3. **SPOOLES on one thread, always.** ccx 2.21's multithreaded SPOOLES now and then returns a wrong solution with no warning. With `CCX_NPROC_EQUATION_SOLVER=1` and `OMP_NUM_THREADS=4` (threaded matrix set-up and stresses only) 20 solves of each agreed to 3e-13. The worker never set threads, so runs so far used one; the solve job now also sets `CCX_NPROC_EQUATION_SOLVER=1` explicitly, so a thread setting added later (say per machine size in M2.12) cannot switch SPOOLES to threads. Four SPOOLES threads would have been 2.1 times faster at 1.8 times the memory; the benchmark's 4-thread SPOOLES rows are kept for that comparison only.
4. **No iterative solver for runs, for now.** CalculiX stops both at a relative residual of 1e-4, fixed in its source (`preiter.c`) with no keyword to change it. Run on all 13 verification cases (coarse tier, local experiment), iterative Cholesky failed 6 and iterative scaling 2, by 0.11 to 0.45 percent against the 0.1 percent checks, worst with prescribed displacements (V-24) and constrained thermal expansion (V-08). They are 4 to 15 times faster than single-threaded SPOOLES from 25,000 to 145,000 elements and need a sixth to a twelfth of the memory, but using them would make large runs less exact than the cases verify, which needs the maintainer (item 7). ARCHITECTURE's "solver choice by model size" therefore stays planned, not built.
5. **Threads elsewhere stay off for now.** Matrix set-up and stresses could use `OMP_NUM_THREADS` safely as far as tested, but they are a small part of a SPOOLES run; whether and how many is M2.12's choice per machine size (ADR-033 item 5), with this benchmark's data.
6. **The deck generator can name a solver.** `generate_deck(spec, mesh, solver=...)` writes `*STATIC, SOLVER=<name>` for SPOOLES, PASTIX, ITERATIVE SCALING or ITERATIVE CHOLESKY, so the benchmark solves the same deck with each and the generator stays the only writer of `.inp` content. Runs pass no name, so every deck and snapshot is unchanged and the build's default (SPOOLES) solves it.
7. **Open: PaStiX and the 2-million-element target.** With SPOOLES and the iterative solvers no solver met both the verification tolerances and the target: SPOOLES runs out of memory an order of magnitude short of it, and the iterative solvers are 0.1 to 0.5 percent off. CalculiX 2.21's PaStiX interface needs the CalculiX fork of PaStiX (it sets `IPARM_REUSE_LU`, which upstream PaStiX 6.4 lacks), at github.com/Dhondtguido/PaStiX4CalculiX. That host first looked refused; Shubham chose to unblock it (option a), and it turned out reachable over git (only plain HTTPS downloads from it are refused).    PaStiX's answers equal SPOOLES's on every mesh, `make verify` with it as the worker's `ccx` passed 116 of 116 checks in all 13 cases, and unlike threaded SPOOLES its threaded solves repeat to about 1e-12. The crash at 331,000 nodes is most likely 32-bit integer overflow; CalculiX's recipe builds PaStiX with 64-bit integers, which also needs 64-bit-integer SPOOLES, ARPACK, Scotch and BLAS, and was not tried. Extrapolating the measured memory (about nodes^1.3, inferred, not measured), a direct solve of the 2-million-element block needs roughly 180 to 220 GiB with either solver. Shubham chose (a) for later (2026-10-15): it is parked in `docs/PROGRESS.md` as its own task after M2, and runs stay on SPOOLES until then. ### ADR-049: Estimator v1 is two power laws in the node count, fitted to timed solve jobs; machine sizes are listed by memory and recommended by memory alone
2026-10-15 · Accepted (under Shubham's standing M2 instruction; reviewed and accepted by Shubham on 2026-10-16). ADR-063 refitted it per solver (estimator version 2) and replaced item 8; ADR-081 fits the job time per element order (version 5).

M2.12 adds the estimate before a run and the machine-size recommendation that DECISIONS asks for (Estimate, Size recommendation) and ARCHITECTURE describes (Estimator). Choices it needed:

1. **Fitted to the solve job, not to the solver alone.** The M2.11 rows time `ccx` by itself; a run is billed for its job's handler. `worker/benchmarks/solver/steps.py` runs the solve job's own steps in its order (mesh read, deck, `run_calculix` with the worker's environment, results, viewer files) on the M2.11 block at ten meshes, 5,212 to 207,025 nodes, first and second order, and records each step's time and the solver's peak memory in `steps.json`. Downloads and uploads are not in it (local files); they are a second or less on the verification models.
2. **Two laws in the node count.** Peak memory and job time are each `constant + coefficient × nodes^exponent`, the constant found by a fine search and the rest by least squares on logarithms (`fit.py`). Fitted: memory 9.6 MB + 517 × nodes^1.367 bytes, time 0.75 s + 4.67e-8 × nodes^1.969 s. Memory is within 2 percent of every row, and within 2 percent of M2.11's four single-threaded SPOOLES rows, which were measured separately; time is within 21 percent (first-order meshes run a little slower per node than second-order ones, and two runs of one 19,000-node mesh differed by 20 percent). Element count and order are not inputs: per node both orders measured about the same, so one law serves both. The coefficients live in `packages/spec/estimator.json` with a version that `fit.py` bumps when they change; a worker test fails if the file is not the fit of `steps.json`, and nobody edits the file by hand.
3. **Shape is not an input yet, so the estimate is high for slender parts.** The block is stocky, the hard case for SPOOLES. On the 13 verification cases (`make verify`, coarse tier) the job was billed 1 to 27 s against estimates of 1 to 53 s: about right below 10,000 nodes and about twice the billed time for the 12,000 to 39,000-node cylinder, cantilever and stub. The UI says so ("slender parts usually need less memory"). A shape term (for example the matrix profile) is a later refit, checked by M8.9.
4. **Machine sizes are a list by memory.** `machine_sizes` gains cores and memory; migration 0013 replaces the single `local` size (ADR-033) with small (2 cores, 8 GiB), medium (4, 16 GiB; the default for mesh jobs, the laptop class), large (8, 32 GiB) and xlarge (16, 64 GiB), at placeholder rates of 0.5, 1, 2 and 4 credits an hour (in proportion to memory) until beta cost data sets real ones. Jobs already billed keep the size name and rate they were queued with.
5. **Recommended by memory, conservatively.** The solver runs on one thread on every size (ADR-048 item 3, and threads elsewhere stay off: item 5's choice is "none yet", since a SPOOLES run is almost all factorisation), so the time is the same on every size and only memory and rate differ. The recommended size is the cheapest whose usable memory (85 percent of it, as the M2.11 benchmark's own limit) holds the fitted peak times a margin of 1.25. With the fit that is up to about 145,000 nodes on small, 240,000 on medium, 400,000 on large and 660,000 on xlarge (stocky second-order meshes of about 100,000, 170,000, 280,000 and 470,000 elements). When no size fits, nothing is recommended and the panel says a coarser mesh or linear elements need less. The user may choose any size (DECISIONS); a size with too little memory is allowed with a note that the run may stop for lack of memory. Who pays for such a run is the out-of-memory path of M8.5.
6. **API and record.** `GET /api/simulations/{id}/estimate` returns the estimate (`RunEstimate`) for the current ready mesh: estimator version, nodes, peak memory, seconds, whether the mesh is past the fitted range, each size's cores, memory, rate, cost and fit, and the recommended size. `POST /api/simulations/{id}/runs` takes an optional `{ "machineSize": ... }` (an empty body still works), queues the solve job on that size or the recommended one (the largest when none fits), refuses an unknown name, and freezes the estimate with the run (`runs.estimate`, shown in the run record next to the cost). The cost on each size uses metering's own arithmetic (`costOf`), so estimate and bill round the same way.
7. **Not done here, on purpose.** Thread count and memory limit per simulated size (M8.5), refusing a run on a low balance (credit grants and the wallet are M8.1; balances start at 0, so a check now would refuse every run), the stop limit (M8.2), estimator terms for modal runs (M6.3), and checking estimate against measured cost on the benchmark set (M8.9).
8. **The laptop tier.** DECISIONS' Model size row says the laptop tier is about 300,000 to 500,000 elements with the direct solver. This estimator, like ADR-048, puts a 16 GB machine at about 170,000 stocky second-order elements with SPOOLES. The row is not changed here. PaStiX (ADR-048 item 7) would not move it: it is faster but needs about 1.25 times SPOOLES's memory, and when it is adopted the estimator is refitted for it.

### ADR-050: Stress components, principal stresses and total strain components as new viewer fields; CalculiX's tensor shear strains
2026-10-16 · Accepted (under Shubham's standing M3 instruction; reviewed and accepted by Shubham on 2026-10-16).

M3.1 adds principal stresses and the stress and strain components to the results (DECISIONS product table, Results row; ARCHITECTURE section 7, results pipeline steps 1 and 2). Choices it needed:

1. **Strain comes from CalculiX, as total strain.** The deck asks for `*EL FILE` `S, E` instead of `S`, so CalculiX writes a `TOSTRAIN` block (EXX to EZX, extrapolated to the nodes and averaged like the stress) beside `STRESS`. That is the only change to the deck text, so `DECK_FORMAT` becomes 2 and every snapshot changes by that line and its first line; the four solver-output fixtures were re-run with ccx 2.21 on the new snapshots and differ from the old ones only by the added block and the date. `E` is the total strain, elastic plus thermal (checked with ccx 2.21 on one heated tetrahedron: `E` = `ME` + α ΔT; `ME`, the mechanical strain, is not asked for). Total strain is what a strain gauge or a measured growth sees, and it is what most tools show as "strain"; elastic strain alone can follow when a task needs it. Recomputing strain from stress with Hooke's law was not chosen: it would leave out the thermal part and need the material at every node.
2. **Shear strains are tensor components.** CalculiX's EXY is ½ ∂u/∂y + ½ ∂v/∂x, half the engineering shear strain γxy (checked with ccx 2.21: a tetrahedron sheared by ∂u/∂y = 0.01 gave EXY = 0.005 and SXY = G × 0.01). The fields keep CalculiX's values unchanged, and the viewer labels them "Shear strain εxy (γxy / 2)" so nobody reads a factor-two error into them.
3. **Principal stresses are derived from the nodal stress.** `principal_stresses` (worker `results/fields.py`) gives σ1 ≥ σ2 ≥ σ3 of the nodal stress tensor in closed form (Smith 1961, trigonometric solution of the characteristic cubic) in double precision; a tensor without shear is sorted as it is, and the middle value comes from the trace. Like von Mises, it is computed from CalculiX's averaged nodal stress, not averaged itself. Tested against known states and, for random tensors, against the three invariants and von Mises. Principal directions are not kept; nothing asks for them yet.
4. **Three new fields in `fields.bin`, still version 1.** `stress` (6, pressure), `principalStress` (3, pressure) and `strain` (6, the new `strain` kind) follow `displacement` and `vonMises` (`packages/spec/result-fields.md`). Readers find fields by name, so the layout and version stay. The file grows from 4 to 19 floats per surface vertex. Runs solved before M3.1 have only the first two fields; asking for another quantity shows "This run was solved before ClearFEA kept stress components, principal stresses and strains … Run the simulation again to see it.", and von Mises and displacement still show. The run summary (`SolveResult`) is unchanged.
5. **A `strain` kind in `units.json` version 3.** SI unit m/m; mm/mm and in/in (factor 1), µε (1e-6) and % (0.01). The systems show mm/mm (metric-mm), m/m (SI) and in/in (US); a display-unit choice in the result view stays with M3.7. The shared conversion fixture has four strain cases.
6. **The quantity list.** "Show on the model" lists, grouped: Displacement (magnitude), Stress (von Mises, maximum, middle and minimum principal stress σ1, σ2, σ3, normal stresses σxx, σyy, σzz, shear stresses τxy, τyz, τzx) and Strain (εxx, εyy, εzz, εxy, εyz, εzx), all in global axes. Components are drawn signed in the same nine bands from the smallest to the largest value. Displacement components and equivalent strain were left out as not asked for.
7. **Verification.** The harness gains the quantities `stress.<c>`, `principal.<k>` and `strain.<c>`, read from the run's `fields.bin` like the rest. New checks: V-24 (σxx and σ1 = Eε, εxx = δ/L, εyy = −νδ/L, 0.1 percent), V-08 (σxx and σ3 = −EαΔT, total strain (1 + ν)αΔT across the width and thickness, 0.1 percent; a total strain of zero along the held length is not checked because a relative tolerance needs a reference other than zero) and V-01 (Lamé: σ1 hoop at the bore and the outside, τxy = (σr − σθ)/2 and εxy = τxy (1 + ν)/E at 45 degrees on the bore, with V-01's stress tolerances). V-01's σ3 = −p at the bore was tried and left out: the extrapolated nodal radial stress there, where it changes fastest, read 4.9 percent (coarse) and 1.7 percent (full) short, converging, so it would need a tolerance too wide to mean anything; V-08 checks σ3 instead. `worker/spikes/solve_check` adds the total strain and principal stresses of the ν = 0 bar at every node and checks that the new viewer fields carry the reader's nodal values.

### ADR-051: Reactions from every held node with every applied load taken out; moments about each support's centroid; load totals and a balance check in the result
2026-10-16 · Accepted (under Shubham's standing M3 instruction; reviewed and accepted by Shubham on 2026-10-16).

M3.2 adds reaction moments per support, applied-load totals and a balance check shown on every result (DECISIONS product table, Results and Report rows; ARCHITECTURE results pipeline step 5). Choices it needed:

1. **Every held node's reaction is printed, also for fixed-only setups.** Moments need each node's force and position, so the deck now always defines `RALL` (every held node) and asks for `*NODE PRINT, NSET=RALL, GLOBAL=YES` with `RF`; the per-set `TOTALS=ONLY` lines of the M1 layout are gone. Holds are unchanged (`*BOUNDARY S<n>, 1, 3` for fixed supports). `DECK_FORMAT` becomes 3; every snapshot changes by its first line, and the fixed-only ones also by the `RALL` set and print (reviewed: no other line differs). The two solver-output fixtures whose decks changed (`solve`, `elastic-fixed`) were re-run with ccx 2.21: their `.frd` files are the same but for the date, so only the `.dat` files were replaced. Reactions are now always shared per node between the supports holding it (ADR-039 item 5), so two fixed supports sharing an edge no longer count it twice.
2. **Uniform pressure on held nodes is taken out of the reactions.** CalculiX's RF at a held node includes the load applied there (ADR-040 item 4), and the pressure part was the one still missing (ADR-029, M1.7). `deck/loads/pressure.py` now works out CalculiX's own nodal loads for a `*DLOAD` pressure: −p n times each node's shape function over the curved element face, integrated with a three-point rule (area coordinates 1/6 and 2/3, weights 1/3). The rule was found by solving, not from memory: on a quarter ring pressed on its curved outside, CalculiX's RF at the free nodes (its applied load there) matched the three-point rule to 1.6e-7 of the largest nodal load on ten-node elements, where the seven-point rule of a force (ADR-040) and a four-point rule were 2.7e-4 off; on four-node elements every rule agrees. `worker/spikes/load_check` keeps that comparison as its pressed ring. The pressures stay `*DLOAD` lines, so the deck's load text is unchanged. With this, the reaction of the M1 fixture's fixed face reads (100, 0, −50) N, balancing its pressures (−100, 0, 50) N, where it read (100, 0, −33.3) N before, and `spikes/solve_check`'s cantilever clamp carries the whole 4,000 N, not 3,986.9 N.
3. **Moment about the support's centroid.** Each support's moment is Σ (x_n − c) × f_n over its nodes at undeformed positions (a linear analysis), about c, the area centroid of the support's faces (integrated over the curved element faces with the seven-point rule), which the result stores as `point`. A moment about a point on the support reads like the moment the support carries; about the origin it would mostly be the force's lever. An elastic support's moment comes from its springs' nodal forces (ADR-043). `SupportReaction` gains optional `moment` and `point`; runs solved before M3.2 have neither.
4. **Load totals as the solver applies them.** `SolveResult.loads` lists each load's total force and moment about the origin, summed from the nodal loads the solver gets: force, remote and hydrostatic loads as the deck writes them, pressures by the rule above, gravity and centrifugal loads with CalculiX's volume rule (summed per integration point, which equals the nodal forces' sum and moment without the per-node work). A temperature change applies none. Totals of what was entered (F = p A from the CAD area) were not chosen: the balance check must compare what the solver actually loaded with what it reacted, so a load that missed part of a face shows.
5. **The balance check.** `SolveResult.balance` holds the applied force and moment, the reactions' force and moment (both about the origin), and two ratios: the imbalance's size over the larger of the loads' gross size (the sum of the sizes of their nodal forces, or of their integration points' forces for body loads) and the sum of the reactions' sizes (so a temperature change or prescribed displacement, with no applied load, is measured against its reactions, as the harness does, ADR-039), and the imbalance moment's size over the largest of the applied moment's size, the sum of the reactions' moment sizes about the origin, and that force scale times the mesh's bounding-box diagonal (so a load through the origin does not leave the moment measured against nothing). The gross size matters where a load cancels itself: V-01's pressure all round the bore adds up to 1e-10 N and its reactions to 5e-4 N, so the first version, measured against the applied force's size, read the imbalance as 100 percent of almost nothing in the first `make verify`; against the pressure's gross size it is 7e-10. On the fixtures, spikes and verification cases the ratios come out at 1e-13 to 2e-7, the solver's printed digits. Numbers only, no verdict: the Run panel shows "Out of balance: force x % of F, moment y % of M".
6. **The Run panel.** Under the result figures: each support's reaction force, its moment and the point it is about; each load's total force ("Applied, <name>"); the applied and reaction totals about the origin; and the out-of-balance line. Names come from the run's frozen setup, not the current one. A run solved before M3.2 shows its reaction forces and "Run again to see reaction moments and the balance of loads and reactions."
7. **Verification.** The harness gains the quantities `moment.x`, `moment.y` and `moment.z` (a support's reaction moment about its centroid) and an automatic row on every case: the run's own balance check, force and moment, within the 0.1 percent of the existing balance row (which stays, as an independent check from the surface triangles). V-04 checks the clamp's torque −120 N·m and bending moment −127.79 N·m (the remote point's lever included) to 0.1 percent. `worker/spikes/solve_check` checks the cantilever clamp's whole load, its moment W L/2 about the clamped face's centre and the balance to 1e-6; `spikes/load_check` adds the pressed ring; `spikes/deck_check` sums the per-node reactions.

   Colouring and placing the section for another quantity or deformation scale takes 4 to 16 ms. Writing `nodes.bin` for 2.7 million nodes takes the worker about 3 s, against hours of solving at that size (ADR-048).
2. **Cut in the browser at every size.** At the 2-million-element target a cut takes about a quarter of a second, and the browser holds about 150 MB for the mesh and a field, so the slider stays usable and nothing needs a machine. A server-side slice was not chosen: each move of the plane would wait for a job, and in the cloud for a machine to start, which is seconds to minutes against a quarter of a second. A web worker was not needed either: the laptop tier (about 170,000 elements, ADR-049) cuts in about 35 ms, and the 2-million-element model in a quarter of a second, on the main thread. What is large at 2 million elements is the download: about 150 MB for the first cut, a couple of seconds on a local network and around ten seconds at 100 Mbit/s. That is accepted for the largest models; compressing the mesh can follow if the M9.1 demonstration shows it is needed.
3. **The mesh is the run's own `mesh.bin`, the values are a new `nodes.bin`.** `GET /api/runs/:id/mesh` serves the mesh the run was solved on (meshes are never changed or deleted, ADR-047), so nothing is stored twice. The solve job writes `nodes.bin` (`packages/spec/result-fields.md`): the same fields as `fields.bin`, in the same format, at every node of the mesh in mesh order, interior nodes included. `GET /api/runs/:id/nodes?field=<name>` returns one field in the same format, read from storage by range, so the viewer downloads only the displacement and the field shown (all node values of a 2-million-element run are about 200 MB, one scalar field about 11 MB). Values are the result reader's nodal values; nothing new is computed. Runs solved before M3.4 have no `nodes.bin`, and the cut plane says to run again.
4. **How a mesh is cut.** Each 10-node tetrahedron is split into eight 4-node tetrahedra through its mid-edge nodes (four at the corners and four around the diagonal between the mid-nodes of edges 0-1 and 2-3), so the mid-edge nodes' values and curved element edges take part; each small tetrahedron is cut by the plane into a triangle or a quadrilateral. A section vertex lies on an edge between two mesh nodes and is stored as those two nodes and how far along the edge it is, so any field, and the deformed shape, is drawn on it by linear interpolation along that edge without cutting again. This is the one place values are interpolated for display (ADR-031 item 1 reads node values only), because a plane passes between nodes. Within each small tetrahedron a linear field is drawn exactly (unit tests).
5. **One plane, across x, y or z.** The cut plane panel picks the axis, a slider places the plane anywhere across the model's extent (its position is shown in the display length unit), and "Keep the other side" turns it round. The plane is placed on the undeformed shape, and both the section and the model are drawn on the deformed shape: the model is hidden beyond the plane by each point's undeformed position (a shader test on a `reference` attribute), so the section meets the model's surface exactly at any deformation scale. Slanted planes and several planes at once were left out; they can follow if wanted.
6. **The legend and the markers cover what is drawn.** With a cut, the bands span the surface left standing and the section, and the min/max markers mark the extremes of the same values, on the section when an extreme lies there, so ADR-052's rule that markers are the legend's ends still holds. Probes stay on the surface: a click on the section, or on a part the plane hides, probes nothing, so a probe still reads one node's own value (ADR-052 item 2).
7. **Verification.** Unit tests cover reading `mesh.bin`, the section's area and orientation for planes through nodes, between nodes and slanted, linear fields drawn exactly, the mid-edge nodes' part, the deformed placement, the viewer's panel, legend and markers with a cut, and the API's whole and per-field replies. The worker writes `nodes.bin` (physics-critical: `worker/clearfea_worker/results/surface.py`); `spikes/solve_check` checks it holds every field at every node of the cantilever to float32 precision. The harness gains checks inside the body (`inside: true`, the mean over the mesh nodes in a box, from `mesh.bin` and `nodes.bin`) and, for a case with one, an automatic check that every field served on its own equals the whole file; V-10 checks σz inside the column at a quarter of its height, off the middle so that values on the wrong nodes would show. ### ADR-054: Safety factor against yield as yield strength over von Mises at every node, capped at 15; library yield strengths are MIL-HDBK-5G's Fty for one named product
2026-10-16 · Accepted (under Shubham's standing M3 instruction; reviewed and accepted by Shubham on 2026-10-16).

M3.5 adds the safety factor against yield to the results (DECISIONS product table, Results row and Materials row: "yield strength for the safety-factor plot"; ARCHITECTURE results pipeline step 2). Choices it needed:

1. **Yield strength is an optional material value.** `IsotropicMaterial` gains `yieldStrength`, a pressure quantity greater than zero, absent or null until entered, like density and thermal expansion. It does not reach the deck (the deck generator ignores it, so no snapshot changed) and pre-run validation does not ask for it: a run without it is valid and simply has no safety factor. The Material panel has a "Yield strength" field; changing it drops a library source like the other values (ADR-046 item 6).
2. **The safety factor is Sy / σvm at each node.** The von Mises (distortion energy) criterion for a ductile isotropic metal, from the same nodal von Mises stress the viewer shows (CalculiX's averaged nodal stress, ADR-050), in double precision in the worker (`worker/clearfea_worker/results/safety.py`, physics-critical). A node shared by bodies of different materials takes the smallest of their yield strengths. Other criteria (Tresca, maximum principal stress for brittle materials, fatigue) were not asked for. It is a number, never a verdict: no "safe", "pass" or limit line anywhere (CLAUDE.md), and the colours only reverse.
3. **Capped at 15.** Where the factor would exceed 15, or the stress is zero, the field holds 15, so the colour bands and the legend stay finite and readable; the legend says "Factors of 15 and more are shown as 15" when the cap shows, and the Run panel says "15 or more". 4. **All materials or none.** The field is written only when every body's material has a yield strength; a factor for part of a model would read as one for all of it. Otherwise the view says the run has no safety factor, that it needs a yield strength for every material, and to run again (the same message covers runs solved before M3.5).
5. **A new field and kind.** `fields.bin` and `nodes.bin` gain `safetyFactor` (1 component, kind `ratio`) after `strain`; still version 1, since readers find fields by name, so probes, markers and cut planes work on it unchanged. `units.json` version 4 adds the dimensionless `ratio` kind (SI unit "1"), shown without a unit. `SolveResult.safetyFactor.min` holds the smallest factor over every node with where it is (whole mesh, like the von Mises figures, ADR-052 item 1).
6. **Drawn with the smallest values red.** The bands are the same nine colours in reverse, so the most loaded region is red as in the other quantities' convention of red for what matters most. The quantity sits in its own "Safety factor" group of the list.
7. **Library values: MIL-HDBK-5G Fty for one named product.** Each library material takes the tensile yield allowable Fty from the same handbook (ADR-046 item 1; no other source), read from the scanned tables, for one product, temper and thickness range named in its `source` (for example 6061: sheet, T6 and T62, A basis, 35 ksi), A basis where the table prints one and S basis otherwise, the smaller of the L and LT values. Where an entry covers tempers of different strength, the most used temper is taken and the source names it with the range of the others (17-4PH H1075, the temper whose density the entry already used; 15-5PH H1025; 6061 T6; 5052 and 5086 H32; AZ31B H24; Ti-6Al-4V annealed; 4130 normalized at 0.187 in and under). Taking the weakest printed value of every entry was considered and left: it would give, for example, 6061 the T4 value (16 ksi) under a name most users read as T6. The values are minimum allowables, not typical values, and the library panel now says so. Corrections to ADR-046's citations found on the way: the bare 2024-T3 sheet Fty is in Table 3.2.3.0(b1), page 3-69, and the 7050 A values in Table 3.7.3.0(b2) are higher than the (b1) row taken here, which the table marks as S basis.
8. **Verification.** V-24 checks Sy / σ = 36 / 14.5 along the bar's side to 0.1 percent (harness quantity `safetyFactor`); worker unit tests cover the field, the cap, the smallest factor at the largest von Mises stress, the shared-node rule and the no-yield case; viewer tests the reversed bands, the unitless legend and markers and the messages; E-01 enters a 250 MPa yield strength and checks the smallest factor's marker against 250 MPa over the largest von Mises marker (screenshot `e01-safety.png`).

### ADR-060: Bonds are tied with equations the deck generator writes, slave nodes following the closest point of the other face
2026-10-16 · Accepted (under Shubham's standing autodrive instruction; reviewed and accepted by Shubham on 2026-10-16).

M4.3 adds per-body meshing and ties in the deck (PLAN M4.3; DECISIONS product table, Assemblies row: "Each body meshed separately; touching faces auto-detected and tied"). Choices it needed:

1. **Meshing is already per body.** Each body of an assembly is a Gmsh volume of its own with its own faces (ADR-058 item 1), so the mesh job meshes each separately and the faces of a bond get nodes of their own; nothing in the mesh job changes and `MESH_SETTINGS_VERSION` stays. Two faces with the same outline and size are often triangulated alike, but nothing relies on it.
2. **Equations, not CalculiX's `*TIE`.** The first experiment used `*TIE` (ccx 2.21) on two blocks end to end on three symmetry planes, meshed differently each side: displacements and stresses were right, but the reactions of the symmetry planes summed to 0.037 N where they must be zero (1.6 × 10⁻⁴ of the 400 N load). CalculiX's printed nodal force (RF) at a held node is the element forces only; a held master node also carries part of each tied slave node's force, which CalculiX passes on inside the solve and does not print. Correcting for it needs the tie's coefficients, which `*TIE` keeps to itself. So the deck generator writes the ties itself as `*EQUATION` lines (`worker/clearfea_worker/deck/loads/tie.py`), and the result reader adds each held node's share back: λ = the slave node's printed force less its applied load, along the equation's dependent direction, passed to each other term as −coefficient × λ, which is what CalculiX does inside. On the same model the reactions then balance to 3 × 10⁻⁹, and on a version turned 30° about z, so that two planes hold nodes through a `*TRANSFORM`, to 3 × 10⁻⁹ (second order) and 1.4 × 10⁻⁸ (first order).
3. **What a tie says.** For each bond not removed (ADR-059), every node of the slave face follows the master face: its displacement equals the master element face's displacement at the point closest to it, u_s = Σ N_m(ξ) u_m with the master face's own shape functions (three or six nodes; the point found by Gauss-Newton on the curved six-node face). The node is tied when that point lies within 0.1 of the longest edge of its master element face; beyond it (an overhang) it is left free. Bonded faces touch within 1e-4 of the model size (ADR-059); the rest allows for a first-order face's chord across a curved face. No `ADJUST`: nodes stay where the mesh put them, so the run's mesh file and the solver agree on positions.
4. **Which face follows.** The face with the finer mesh (smaller mean element face) is the slave, the usual rule for ties, since a coarse slave lets a finer master's nodes pass between its nodes; when the two are within a quarter of each other, the face with the smaller area, then the larger tag.
5. **Supports on tied nodes.** Equations are written in each node's own deck directions (the *TRANSFORM of a frictionless or prescribed support off the axes, ADR-039), one per direction of the slave node that no support holds; a direction held by a support is not tied (it is held), and a node held in every direction is not tied at all. A master node's terms are written in its own directions too. Measured: the two-block bar on three frictionless planes, turned 30° so that two planes are inclined, gives the 1D end displacement to 0.01 percent and reactions in balance.
6. **No cascades.** CalculiX resolves an equation whose terms depend on other equations, but the reader's correction would then need the same resolution. So a node already tied, or already a master node of another tie, is not tied again, and a slave node whose master element face has a tied node is left untied. That happens only where three bodies meet along an edge. The deck comment of each bond counts the slave nodes tied, held by supports, off the master face and left to another bond.
7. **Runs freeze the bond list.** A spec saved before M4.2 has no bond list, which the setup reads as every candidate detected (ADR-059). The API now writes `specBonds` into each run's copy of the spec, so the deck ties what the setup showed; the worker ties exactly the run's list (none without one).
8. **Deck format unchanged.** A deck without tied bonds is byte for byte what it was; with them it gains the equations, a node set `TIED` and its printed forces. The format number stays 3, as for the load types M2 added; snapshots `bonded-c3d10` and `bonded-slide-c3d4` are new and no existing snapshot changed.
9. **Verification.** V-11 is V-02's cantilever cut across into two bodies at x = 3 in, the root block meshed finer, checked against V-02's single-body values and tolerances: tip deflection −0.73 percent (V-02: −0.75), bending stress 2 in past the bond −0.15 and +0.09 percent, the clamp carrying the load. V-12 is a quarter bar of two materials with the same ν/E end to end on symmetry planes that cross the bond: the exact field is uniform stress in each body, which the elements and the tie reproduce, so stress, strain, end displacement, sideways contraction and the reaction are checked to 0.1 percent, all within 0.02 percent. Near the bond, a tie between unmatched meshes disturbs the stress one or two elements deep (item 2's bar, ν = 0.3, in tension, 5 mm elements against 3 mm: −13 to +12 percent at the bond's nodes with second-order elements and −7 to +4.5 percent with first-order; from 8 mm away, within 0.1 percent of uniform with second-order elements and 0.6 percent with first-order); M4.5 states this in the report text.
10. **Not done here.** Reporting bodies that are not bonded or held before a run is M4.4; the rigid-body check (ADR-039) still looks at the whole model, which the ties now join.

### ADR-061: A body no support or bond reaches is refused before the run; the rigid-body check looks at each bonded group
2026-10-16 · Accepted (under Shubham's standing autodrive instruction; reviewed and accepted by Shubham on 2026-10-16).

M4.4 reports unbonded or unrestrained bodies before a run (PLAN M4.4). Bodies of an assembly are meshed apart and share no nodes (ADR-058), so a body is held only by its own supports or by bonds to a held body; until now the rigid-body check (ADR-039) looked at the whole model, so a free body next to a held one passed and CalculiX solved a singular model. Choices it needed:

1. **Pieces are bodies joined by tied bonds.** In the setup, bodies joined by bonds the user has not removed (`bondIsTied`, so detected bonds count, as the deck ties them) are one piece. A piece is held when a support of any kind, elastic included, has a face on one of its bodies. `unheldBodies(spec, topology)` in `packages/spec` returns the pieces that are not; it uses the body of each face from `topology.json`. It says nothing for a single body (the "no support" line already covers it), before any support has faces, or for a topology that does not give each face's body.
2. **Refused, not warned.** A free piece makes the run meaningless, so it is a pre-run problem like a missing material: the Run button stays disabled and the API answers 409 before queueing (ADR-034). The message is on the Bodies group and names the bodies by their part names: "Body "Pad" is not bonded to a held body and no support holds it, so it is free to move. Add a support on one of its faces", adding ", or restore a removed bond under Bonds that joins it to a held body" when a removed bond touches the piece; bodies bonded only to each other are named together. The free body's own row is marked incomplete too. A body that is not bonded but has its own supports is not reported: separately held parts are a valid model.
3. **The deck generator checks each piece.** `body_groups` (`deck/loads/tie.py`) joins bodies by the ties the deck writes (a bond joins its bodies only when at least one equation is written; a bond whose slave nodes are all held by supports ties nothing) and by shared nodes (a mesh may share them; Gmsh meshes do not). With one piece the check is exactly ADR-039's, on the whole model, with the same message. With more, each piece's held directions and grounded springs are checked on their own, about the centre and size of that piece's nodes, and the refusal names each free body by tag and its free motions ("The supports do not hold body 2 in place: it can still slide along z"), or says that nothing holds it at all. The run is refused before any deck is written; a piece whose supports leave some motion free, such as one frictionless face, is found only here, since the setup has no face normals.
4. **Not checked.** A bond is taken to hold its two bodies together in every direction. A tie written over too few nodes to stop the bodies turning about one another (a bond whose nodes are almost all held, or all off the other face) is not found. Deck text and snapshots are unchanged: the check refuses setups, it writes nothing.

### ADR-063: PaStiX is the default equation solver, with SPOOLES and both iterative solvers as user options; runs are limited per solver and element order to what a 16 GB machine solves; the 2-million-element target is dropped
2026-10-16 · Accepted (Shubham's decision of 2026-10-16, made before M4, including offering the iterative solvers with an accuracy warning and stopping the benchmark at 500,000 elements; the details below await his review of the pull request).

Shubham decided two things before M4: make PaStiX the default solver, with SPOOLES, iterative scaling and iterative Cholesky as options; and drop the 2-million-element target in favour of conservative element limits per solver, element order and node count that a 16 GB machine solves without crashing, leaving larger machines (on AWS) for later. This replaces ADR-048 items 2, 4 and 7 and ADR-049 item 8, and the DECISIONS Model size row and Phase 0 condition 4. Choices it needed:

1. **The build.** `worker/ccx/build.sh` builds CalculiX 2.21 from Ubuntu's `calculix-ccx` 2.21-1 source package (the same source and Debian patches as the packaged `ccx` before it) with `-DPASTIX`, linked to PaStiX4CalculiX at `d6b493b` (32-bit integers, mixed precision) with `worker/ccx/pastix4calculix.patch`, PaRSEC at tag `pastix-6.0.2` (shared, installed beside `ccx`), and Ubuntu's SPOOLES, ARPACK, Scotch and OpenBLAS. It runs in a build stage of the worker image; the runtime stage gets `ccx`, `libparsec.so.2` and the runtime libraries, CUDA's included (the fork includes CUDA headers unconditionally; no GPU is used). The patch over M2.11's also drops the code generator's `import imp`, so Python 3.12 builds it and no other Python is needed. The image grew to 2.06 GB on disk. All commits, the tag and the source package version are pinned; a change is its own pull request with a full verification run (CLAUDE.md).
2. **Every deck names its solver.** `SimulationSpec` gains an optional `solver`: `pastix`, `spooles`, `iterative_cholesky` or `iterative_scaling`. Absent (specs saved before) means `pastix`; new specs start with it. The deck generator writes `*STATIC, SOLVER=<name>` on every deck, so the deck alone says what solved it; deck format 4. The API freezes the run's spec with its solver named, so runs made before this ADR, whose frozen spec has none, are known to have been solved with SPOOLES (the packaged build's default). The Run panel says which solver a run used.
3. **One thread for everything.** The worker now also sets `OMP_NUM_THREADS=1`. Left unset, OpenMP started a thread per core inside PaStiX that spun against PaStiX's single worker: 8 to 14 s were lost even on a 3,000-element mesh, where the whole run then takes under 2 s. One thread keeps a run's time the same on every machine size (ADR-049 item 5), and SPOOLES stays on one thread (ADR-048 item 3). Threaded PaStiX can come with larger machines.
4. **Benchmark.** `steps.py` gained `--solver`; `steps.json` now holds the solve job's steps for all four solvers with this build, on the M2.11 block, first and second order, in the sandbox (4 cores, 13.4 GiB memory limit). Shubham had runs above 500,000 elements skipped, so PaStiX's 4-node rows (to 1.1 million elements, measured before that) are the only ones above it. Selected rows (job time, solver peak memory):

   PaStiX is 4.4 times faster than SPOOLES at 145,471 10-node elements for 1.25 times the memory, as in M2.11.
5. **Limits: from the sandbox to 16 GB.** The limits are for a 16 GiB machine, the laptop class and the `medium` machine size. A mesh is within a solver's limit when its fitted peak memory, raised by the fit's worst shortfall on the measurements (`largestRatio`, up to 1.12) and times the estimator's margin of 1.25, fits in the usable 85 percent of 16 GiB: a fitted peak of about 9.7 to 10.9 GiB. The sandbox's limit is 13.4 GiB, so every measurement that sets a limit was made with room to spare, and the limit is the node count where that holds, turned into elements with the nodes per element of the nearest measured mesh of the order, rounded down to a thousand. No limit is above the largest mesh measured for its solver and order, so none is extrapolated. `fit.py` computes them into `packages/spec/estimator.json` (`limitMemoryBytes`, and `maxElements` per solver), and a test checks every benchmarked mesh under a limit kept to the rule. The limits:

   | Solver | 10-node elements | 4-node elements |
   | --- | --- | --- |
   | PaStiX (default) | 142,000 | 1,103,000 |

   | Iterative Cholesky | 461,000 | 461,000 |

   The measured 145,471-element PaStiX mesh and the 168,077-element SPOOLES mesh are just over their limits by this rule, which is why the limits sit below them. SPOOLES's 4-node and the iterative solvers' limits are the 500,000-element stop, not memory: by memory the iterative solvers would take millions of elements, SPOOLES about 1.3 million 4-node ones. A stocky block is the hard case for a direct solver, so slender parts at a limit need less memory. Within every limit the PaStiX build stays below the 331,000 nodes where its 32-bit integers overflowed in M2.11.
6. **Enforced before a run.** `elementLimitProblem` in `packages/spec` says, in plain language, that a mesh is over its solver's limit, with what to do (a coarser mesh, 4-node elements, or a solver that takes it). The API refuses such a run with it before a job is queued, and the Run panel lists it with the other blockers. The mesher keeps its own 2,000,000-element cap on what it makes; the run limits are separate, since the mesh does not depend on the solver.
7. **Choosing a solver.** The Run panel has an "Equation solver" list above the estimate, PaStiX first, each with its limit for the mesh's element order. Picking one saves it to the spec. The estimate is fetched for it (`GET /api/simulations/{id}/estimate?solver=`, which defaults to the spec's).
8. **The iterative solvers carry a warning (Shubham's choice: offer with warning).** Both stop at a relative residual of 1e-4 fixed in ccx 2.21's source and were 0.11 to 0.45 percent off the 0.1 percent verification checks in M2.11 (ADR-048 item 4). Wherever one is chosen or was used, the app says: "Iterative solvers stop at a fixed relative residual of 1e-4 in CalculiX 2.21. On the verification cases their results were up to about 0.5 percent off, while PaStiX and SPOOLES are verified to 0.1 percent." That is the Run panel, the result figures and the run record. The report (M7) must print the solver and this note; the run's frozen spec holds what it needs. Rechecked with this build (`make verify`, coarse tier, every case forced onto the solver, a local experiment): PaStiX 146 of 146, SPOOLES 146 of 146, iterative Cholesky 130 of 146 (V-02, V-03, V-04, V-08, V-24 and V-26, 0.11 to 0.43 percent against 0.1), iterative scaling 139 of 146 (V-08 and V-24, 0.16 to 0.41 percent). The verification suite runs with the default solver; the iterative solvers are not verified to 0.1 percent and are not claimed to be.
9. **The estimator per solver.** `estimator.json` version 2 holds a memory and a time law per solver (both element orders fitted together, as in ADR-049). The estimate a run freezes names its solver; older estimates without one were for SPOOLES. Fitted memory is within 5 percent of every PaStiX and SPOOLES row and within 12 percent for the iterative solvers, whose small runs are dominated by a fixed 100 MB.
10. **Later, on larger machines.** Larger machine sizes get their own limits when benchmarked on such machines (`limitMemoryBytes` is per table; a table per memory size is the likely shape). For PaStiX that needs a 64-bit-integer build first: ccx's `Makefile_i8` recipe with 64-bit SPOOLES, ARPACK, Scotch and BLAS. Until then the larger sizes are still listed and priced (ADR-049), but every run is held to the 16 GiB limits.

### ADR-064: Steady-state thermal is an analysis type of the same setup, solved as a CalculiX heat transfer step with fixed temperatures on faces
2026-10-16 · Accepted (under Shubham's standing M5 autodrive instruction; reviewed and accepted by Shubham on 2026-10-16).

M5.1 adds the steady-state thermal analysis type and thermal material properties (PLAN M5.1; DECISIONS scope: analyses, thermal loads). Choices it needed:

1. **One setup, one analysis type.** `SimulationSpec.analysis` gains `steady_thermal` beside `linear_static`; the spec stays version 1, since a new enum value and a new item type change no existing data (ADR-026 item 1). The setup tree's new Analysis row switches it. Items that do not belong to the analysis (supports and structural loads in a thermal setup, a fixed temperature in a static one) are kept, so switching back loses nothing, but pre-run validation names each one ("has no effect in a steady-state thermal analysis; delete it, or set the analysis type to linear static") and the deck generator refuses them, so a run never silently drops part of the setup. Which loads an analysis takes is one table, `analysisLoads` in `packages/spec`.
2. **Thermal conductivity, constant and isotropic.** Materials gain an optional `thermalConductivity`, a new `units.json` kind (version 5): W/(m·K) (SI), W/(m·°C), W/(mm·K), BTU/(h·ft·°F) and BTU·in/(h·ft²·°F), the BTU being the International Table BTU (1055.05585262 J) as for every other US unit here. Pre-run validation asks for it, and not for Young's modulus or Poisson's ratio, when the analysis is thermal; the deck refuses zero or less. Specific heat and density are not needed for a steady state. Temperature-dependent tables are M5.5. The material library (MIL-HDBK-5G values, ADR-046) gets no conductivities in this task; they are parked.
3. **Fixed temperature comes with the analysis type.** A steady-state thermal problem has no solution without at least one fixed temperature, and a new analysis type lands with a verification case (CLAUDE.md), so the fixed temperature of M5.2 is built here; heat flux, convection, radiation and heat generation stay in M5.2. It is a load (DECISIONS lists it among the thermal loads): `fixed_temperature` with faces and an absolute `temperature` quantity (°C and °F convert with their offsets; ADR-038). Every node on its faces, corner and mid-edge, is held at that temperature (CalculiX degree of freedom 11 under `*BOUNDARY`). A face with no thermal load is insulated, CalculiX's default. Two fixed temperatures that reach the same node (faces sharing an edge) at different temperatures are refused with a message naming both: CalculiX would keep one without saying which. Temperatures at or below 0 K are refused.
4. **Deck.** `generate_deck` writes, for a thermal spec, the same nodes and elements as a static deck (C3D10 or C3D4: in a `*HEAT TRANSFER` step CalculiX 2.21 solves their temperature degree of freedom; checked on a meshed bar, linear profile within 5e-4 K), one node set per fixed temperature, each used material's `*CONDUCTIVITY` in W/(m·K) and no `*ELASTIC`, then `*STEP`, `*HEAT TRANSFER, STEADY STATE` (with `SOLVER=` when a solver is named, as `*STATIC` has) and its data line `1.0, 1.0` (CalculiX treats every heat transfer step as nonlinear and warns "a nonlinear geometric analysis is requested but no time increment nor step is specified" without it; one increment solves the linear steady state), the `*BOUNDARY` lines, and `*NODE FILE` `NT`. The heading names the analysis, and the units line adds K and W. Static decks are byte-identical, so `DECK_FORMAT` stays 3 and no existing snapshot changed; new snapshots `heat-c3d10` and `heat-two-bodies-c3d4`. Heat flux output (`HFL`) and the fixed nodes' heat flows (`RFL`) wait for M5.3, which reads them.
5. **Bonds and bodies.** Bonds do not carry heat until M5.6, so a thermal setup with a bond not removed between bodies is refused before the run and by the deck generator, rather than solved with insulated interfaces. Bodies share no nodes (ADR-058), so each body needs a fixed temperature of its own; pre-run validation names the bodies without one and the deck generator refuses them (their temperature would be undetermined).
6. **Results.** The reader takes the `NDTEMP` block of the `.frd` file. `fields.bin` and `nodes.bin` of a thermal run hold one field, `temperature` (kind `temperature`, kelvin, one component), and the summary `temperature.min` and `.max` with node and position; `SolveResult`'s `displacement`, `vonMises` and `reactions` become optional, present for every static run as before and absent for a thermal one. The Run panel shows the highest and lowest temperature and the viewer colours the model by temperature (no deformed shape: there is no displacement); cut planes, probes, units shown, saved views (`view.schema.json` `ResultQuantity` gains `temperature`) and the CSV and VTK exports work on the temperature field. The `.frd` file keeps five significant digits, 0.01 K at 300 K.
7. **Estimator unchanged.** A thermal run is estimated with the linear static law (`packages/spec/estimator.json`, ADR-049), which the solver benchmark thread owns. A heat transfer step has one unknown per node instead of three, so the estimate is high, which is the safe side (the platform pays for a machine that is too small). Thermal terms can be fitted when a benchmark measures them.
8. **Verification.** V-13 (plane wall) checks the fixed temperatures with their offsets and the linear profile at three depths through the API, at 0.01 percent of the absolute temperature; its heat-flux check arrives with flux results in M5.3. The harness reads a `temperature` quantity and skips the force balance rows for thermal runs (the heat balance is M5.3). `worker/spikes/heat_check` solves generated thermal decks on a meshed bar with first- and second-order elements and compares every node with the exact profile, which the API path cannot see node by node.

### ADR-065: Heat flux, convection, radiation to ambient and heat generation are loads of the steady-state thermal analysis, written as CalculiX's distributed heat loads
2026-10-16 · Accepted (under Shubham's standing M5 autodrive instruction; reviewed and accepted by Shubham on 2026-10-16).

M5.2 adds the rest of the thermal loads of DECISIONS' scope (the fixed temperature came with M5.1, ADR-064). Choices it needed:

1. **Four load types, spec version unchanged.** `heat_flux` (faces, `flux`, a new `heatFlux` quantity, positive into the body, any sign), `convection` (faces, `coefficient`, a new `heatTransferCoefficient` quantity greater than zero, and an absolute `ambientTemperature`), `radiation` (faces, a dimensionless `emissivity` above 0 and at most 1, and an `ambientTemperature`) and `heat_generation` (`bodies`, body tags, and `power`, a new `heatGeneration` quantity per unit of volume, any sign). New item types in an array keep the spec at version 1 (ADR-026 item 1); `analysisLoads` lists them for `steady_thermal` only, so a static setup marks and the deck refuses them. `units.json` version 6 adds the three kinds: W/m², kW/m², W/mm², BTU/(h·ft²); W/(m²·K), W/(m²·°C), W/(mm²·K), BTU/(h·ft²·°F); W/m³, kW/m³, W/mm³, BTU/(h·ft³), the BTU the International Table one as for conductivity.
2. **Heat generation on picked bodies.** It is usually one part of an assembly (a coil, a resistor), so it names its bodies, as a local mesh size on bodies does, and starts on every body when added; the panel ticks them. A body or face listed in two loads of the same kind: heat fluxes on one face and heat generations in one body add up (the conduction problem is linear in them), as pressures do.
3. **Deck.** Each load becomes the CalculiX keyword for its kind, in SI, on the element faces of its faces (the pressure's element-face numbering): `*DFLUX` `Sn` for a heat flux, `*DFLUX` `BF` on a body's element set for heat generation, `*FILM` `Fn` with the ambient temperature in kelvin and the coefficient, and `*RADIATE` `Rn` with the ambient temperature and the emissivity. Each was checked with ccx 2.21 on a meshed bar against its one-dimensional closed form (now part of `worker/spikes/heat_check`, every node within 0.002 K for the linear profiles). With radiation the deck adds `*PHYSICAL CONSTANTS, ABSOLUTE ZERO=0.0, STEFAN BOLTZMANN=5.670374419e-08` (CODATA 2018, exact since the 2019 SI; temperatures are in kelvin) and starts every node at the mean of the setup's fixed and ambient temperatures (`*INITIAL CONDITIONS`): radiation makes the step nonlinear, and from CalculiX's default initial temperature of 0 K the linearised radiation is zero and the iterations diverge (checked). Decks without radiation get neither line, so every M5.1 snapshot is unchanged; new snapshot `heat-loads-c3d10`. A radiating face sees only the surroundings (no view factors between faces; cavity radiation is not in scope).
4. **What sets the temperature.** Convection and radiation tie a face to their ambient temperature, so a setup or a body is solvable with any of a fixed temperature, convection or radiation (`setsTemperature` in `packages/spec`); pre-run validation and the deck generator now ask for one of the three per body, and a heat flux or heat generation alone is refused (its temperature would be undetermined).
5. **Faces that cannot take two loads.** A heat flux, convection or radiation on a face a fixed temperature holds is refused, naming both (the fixed temperature decides the temperature there, so the load would silently do nothing), and so are two convections or two radiations on one face (CalculiX would keep one without saying which). Convection and radiation may share a face, the usual case of a hot surface in air. These are pre-run problems, not save errors, so a setup can pass through them while it is edited. Temperatures at or below 0 K, a coefficient of zero or less and a missing emissivity are refused by the deck generator.
6. **Verification.** V-15 (wall with convection on both sides and no fixed temperature: both surface temperatures and the midplane), V-16 (plate heated by a flux on its back face, radiating from its front to the room: both faces; the nonlinear case) and V-17 (slab with heat generation between two faces at one fixed temperature: centre, quarter points and faces), each at 0.01 percent of the absolute temperature, every load in units other than SI. Their heat-flow checks wait for M5.3's flux results, as V-13's does.


### ADR-066: Heat flux is a result field from CalculiX; each thermal load's heat flow is worked out the way CalculiX applies it, and the heat balance is measured against half the loads' gross heat flow
2026-10-16 · Accepted (under Shubham's standing M5 autodrive instruction; reviewed and accepted by Shubham on 2026-10-16).

M5.3 adds temperature and heat-flux results and the heat balance check (PLAN M5.3; DECISIONS scope: results). The temperature came with M5.1 (ADR-064). Choices it needed:

1. **Heat flux from CalculiX.** The heat transfer deck asks for `*EL FILE` `HFL`: CalculiX's heat flux q = −k grad T at the integration points, extrapolated to the nodes and averaged over the elements that share a node, as it does for stress. The reader keeps the vector (W/m²) as the `heatFlux` field of `fields.bin` and `nodes.bin` (`kind` `heatFlux`, three components, after `temperature`), and the summary its largest magnitude. Heat flows along q, from hot to cold. On a meshed bar every node is within 1e-5 of the closed form for the linear profiles; four-node elements have one gradient each, so where the flux changes along the model (heat generation) their nodal average is off by up to 4 percent at the ends (`worker/spikes/heat_check`).
2. **Heat flow per load, worked out, not taken from CalculiX alone.** CalculiX prints a node's external heat flow (`*NODE PRINT` `RFL`), which at a node a fixed temperature holds is the heat it supplies plus every load's heat applied there, and at any other node just the loads' heat; it has no per-load figure, and a node on the edge between two faces belongs to both. So, like the structural reactions (ADR-051): a heat flux, and at the solved temperatures a convection and a radiation, are integrated over their element faces with CalculiX's own rule (three points on a six-node face, as for a pressure; one point on a three-node face), a heat generation over its bodies' elements with the body-load rule, and a fixed temperature's heat flow is the `RFL` at its nodes (`*NODE PRINT, NSET=TALL`) with the other loads' heat at those nodes taken out. A node two fixed temperatures hold counts for the first in spec order. The worked-out nodal heat matches CalculiX's `RFL` at free nodes to its printed digits on the bar (checked by experiment, both element orders). Each load's net heat flow into the body (W, negative out) goes in the summary as `heatFlows`, in spec order.
3. **Seven-digit temperatures for the exchange faces.** The `.frd` file keeps five significant digits (0.005 K at 1000 K), which shows as an imbalance where a face is close to its ambient, so the deck also prints the temperatures of every node on a face with convection or radiation (`*NODE PRINT, NSET=XALL` `NT`, seven digits), and the reader integrates those faces from them.
4. **Balance measured against the loads' own size.** Heat in is the sum of the loads' heat flows into the body, heat out the sum of those out of it. Their difference is measured against half the loads' gross heat flow: the sum of the sizes of the local heat flows, at each integration point for a load integrated over faces or bodies and at each node for a fixed temperature, which equals the heat in when no load both heats and cools. A convection that heats part of a face and cools the rest therefore still counts with its own size (the trap the structural check met with self-cancelling pressures, M3.2). With no heat flowing at all, what is left is CalculiX's rounding (1e-13 W on a 2 mm model), so the scale is at least 1e-12 of k T L (largest conductivity, highest temperature, model diagonal). Numbers only: heat in, heat out, the scale and the fraction (`heatBalance`), no verdict.
5. **Units.** `units.json` version 7 adds `heatFlow`: W (SI and metric), kW and BTU/h (US), the BTU the International Table one. The Run panel's units shown for a thermal run are length, temperature, heat flux and heat flow.
6. **What the viewer shows.** The quantity list of a thermal run gains "Heat flux magnitude" and its x, y and z components (group "Heat flux"; also in `view.schema.json`'s `ResultQuantity`, so a saved view keeps them). Under the temperatures: the largest heat flux and where, each thermal load's heat flow ("25 W in", "25 W out"), the heat in and out and the fraction out of balance. A thermal run's export gains heat flux columns in the node CSV and the VTK file, and a "Heat flows (CSV)" file in place of the reactions file. Thermal runs solved before M5.3 have no heat flux or heat flows; the view asks for a rerun.
7. **Deck format 5.** Only the thermal deck's text changes (two node sets and the output requests); the static deck's text is the same apart from its format line.
8. **Verification.** Every thermal case gets two automatic rows: the run's own heat balance within 0.1 percent, and, where the case has a heat flux or heat generation, the heat those bring in against the case's own integration over the run's surface (flux times area, power times volume). V-13 (plane wall) gains its heat flux kΔT/L and the heat through each face, V-15 the flux through the wall and films and each film's heat, V-16 the flux at the radiating face and the heat in and radiated, V-17 the flux at the cooled face and a quarter of the way in and the heat leaving through the cooled faces; all at 0.01 percent. `worker/spikes/heat_check` checks the flux at every node, each load's heat flow and the balance on the bar, and the balance with every thermal load at once.

### ADR-067: Thermal stress is its own analysis type, solved in one deck as a heat transfer step followed by a static step, with a stress-free temperature in the setup
2026-10-16 · Accepted (under Shubham's standing M5 autodrive instruction; reviewed and accepted by Shubham on 2026-10-16).

M5.4 adds thermal stress (PLAN M5.4; DECISIONS scope: steady-state thermal and thermal stress). Choices it needed:

1. **An analysis type, not a link between two runs.** `analysis` gains `thermal_stress`: one setup holds the supports and structural loads and the thermal loads, and one run solves both. Linking a static run to an earlier thermal run would need a run to read another run's results, against frozen runs (CLAUDE.md), and two meshes that must match. The spec stays at version 1 (a new enum value and an optional field, ADR-026 item 1). `analysisLoads.thermal_stress` lists every structural and thermal load except the uniform temperature change, which the solved temperature field replaces (refused by pre-run validation and the deck generator, naming it).
2. **Stress-free temperature.** The new optional `stressFreeTemperature` (an absolute temperature) is the temperature at which the bodies have no thermal strain; strain is α (T − Tstress-free). A thermal stress setup without it is marked under Analysis and refused by the deck generator, as is one at or below 0 K. It is one value for the model; a temperature-dependent expansion with its own reference temperature is out of scope (DECISIONS: properties are constant).
3. **One deck, two steps.** The deck has the heat transfer step of ADR-064 to ADR-066 unchanged, then the static step of the structural setup. CalculiX carries the first step's solved nodal temperatures into the second as the temperature field (checked with ccx 2.21: a free bar with a linear temperature grows by the closed form to 5e-11 and is stress-free). The mesh, sets and materials are written once; each material has `*CONDUCTIVITY`, `*ELASTIC`, `*DENSITY` where given and `*EXPANSION`. Every node starts at the stress-free temperature (`*INITIAL CONDITIONS, TYPE=TEMPERATURE`), which is what CalculiX measures thermal strain from (`*EXPANSION, ZERO=` without an initial temperature gave wrong strains); with radiation that same value is the heat step's starting guess, in place of the mean of the known temperatures. The static step's `*STATIC` line carries `1.0, 1.0, 1.0, 1.0` (one increment of the whole step): after a heat step CalculiX otherwise treats the step as nonlinear and warns. The deck generator was reorganised to compose a deck from the parts of each step; every existing snapshot is byte-for-byte unchanged and DECK_FORMAT stays 5. New snapshot `thermal-stress-c3d10`.
4. **Materials.** A thermal stress setup needs conductivity, Young's modulus, Poisson's ratio and thermal expansion for every material in use, and density only with gravity or a centrifugal load.
5. **Bonds refused for now.** Bonds do not carry heat until M5.6, so a thermal stress setup with bonded bodies is refused as the steady-state thermal one is (ADR-064), and so is a body that no fixed temperature, convection or radiation reaches.
6. **Results.** The `.frd` file holds the temperature and heat flux of the first step and the displacement, stress and strain of the second, and the `.dat` file the heat flows (first step) and reactions (second); the readers take each block by name, so they are unchanged. A thermal stress run's `fields.bin` and `nodes.bin` hold the structural fields and then `temperature` and `heatFlux`, and its summary has both the structural figures (reactions, the force balance over the structural loads only) and the thermal ones (temperatures, heat flux, heat flows, heat balance). The Run panel shows both lists, the viewer offers every quantity of both, with the deformed shape, the units shown cover both, and the export has both the reactions and the heat flows files. The strain shown is total strain, elastic plus thermal (ADR-050). With no load applied (a heated body on one fixed support), the run's force balance is now measured against the sizes of the supports' nodal forces rather than their totals: the support pushes back at every node while its total is rounding, which the old scale measured against itself and showed as 100 percent out of balance. Runs with loads are measured as before (ADR-051).
7. **Accuracy of four-node elements.** A C3D4 element has one strain, so a temperature that varies across it gives a stress off by up to 2.6 percent at the nodes on the bar of `worker/spikes/heat_check`; C3D10 is exact for a linear temperature. The warning already shown for first-order elements covers it.
8. **Estimator unchanged.** The run is estimated with the linear static law (ADR-049); the heat step's time is not counted. Its single unknown per node makes it small next to the static step, and the estimator and its benchmark are left alone in this task.
9. **Verification.** V-18 (a quarter of a thick tube, hot bore, cool outside, frictionless cuts and ends, so plane strain holds everywhere) checks the hoop and axial stresses, von Mises stress, radial displacement at both surfaces, the axial force on an end and the heat flow, against the closed form (Timoshenko and Goodier). The harness gives a thermal stress case both the heat balance and the force balance rows. `worker/spikes/heat_check` solves four of its thermal setups as thermal stress on the bar, with the ends and sides on frictionless supports, and compares every node's stress and displacement with the closed form.

### ADR-068: Conductivity, Young's modulus, Poisson's ratio and thermal expansion may each be a table against temperature, read only by analyses that solve temperatures
2026-10-16 · Accepted (under Shubham's standing M5 autodrive instruction; reviewed and accepted by Shubham on 2026-10-16).

M5.5 adds temperature-dependent property tables (PLAN M5.5; DECISIONS scope: materials with temperature-dependent property tables). Choices it needed:

1. **One table per property, beside its single value.** Materials gain optional `youngsModulusTable`, `poissonsRatioTable`, `thermalExpansionTable` and `thermalConductivityTable`: rows of a temperature and a value, each column in one unit (`temperatureUnit`, and `unit` of the property's kind; none for Poisson's ratio), at most 50 rows, values kept as typed. A table per property, rather than one table of every property, because sources give each property at its own temperatures. Density, yield strength and the safety factor stay constant. The spec stays at version 1 (optional fields, ADR-026 item 1). Saving refuses units of the wrong kind; pre-run validation asks for at least two rows, every row filled in, rising temperatures and values in range (Young's modulus and conductivity above zero, Poisson's ratio between −1 and 0.5), and the deck generator refuses the same, and a temperature at or below 0 K.
2. **Only where temperatures are solved.** Steady-state thermal and thermal stress analyses know each point's absolute temperature, so they use a table in place of the single value, which they then do not need. A linear static analysis, including one with a uniform temperature change (no absolute temperature, ADR-044), uses the single values; its pre-run message says so when a material has only the table. A steady-state thermal analysis reads only the conductivity table.
3. **Linear between rows, constant beyond.** That is how CalculiX reads a table (checked with ccx 2.21: a bar whose conductivity table stopped short of its temperatures carried the heat of the clamped integral, 35 W, not the extrapolated 40 W), and the setup's hint says so. CalculiX wants Young's modulus and Poisson's ratio on the same `*ELASTIC` rows, so the deck generator writes a row at every temperature of either table with both values interpolated the same way, which changes nothing inside the tables and nothing beyond them.
4. **Mean expansion coefficients with their own reference temperature.** A table's coefficients are mean (secant) values from a reference temperature to each row's, as handbooks print them, so `thermalExpansionTable` carries `referenceTemperature` ("Measured from" in the setup) and the deck writes `*EXPANSION, ZERO=` it. With every node starting at the stress-free temperature T₀ (ADR-067), CalculiX's thermal strain is α(T)(T − Tref) − α(T₀)(T₀ − Tref) (checked with ccx 2.21 on a free bar: 2.835e-3 against that formula's 2.835e-3, where ignoring the reference would give 2.55e-3). This replaces ADR-067 item 2's "a temperature-dependent expansion with its own reference temperature is out of scope". A single coefficient is still written without `ZERO=`, so every earlier deck is unchanged.
5. **A conductivity table makes the heat step nonlinear.** Its first iteration uses the conductivity at the starting temperature, so every node starts at the mean of the known temperatures, as with radiation (ADR-065), or at the stress-free temperature in a thermal stress analysis. CalculiX stops iterating when the heat flux residual is 0.005 and the temperature correction 0.01 of their averages, which left the bar of `worker/spikes/heat_check` 1e-4 out of heat balance; such a deck adds `*CONTROLS, PARAMETERS=FIELD` with `1e-5, 1e-5`, which took two more iterations and left it 1.5e-7 out, with every node within 0.0006 K of the exact profile on ten-node elements. Decks without a conductivity table do not change: every earlier snapshot is byte-identical and DECK_FORMAT stays 5; new snapshot `thermal-stress-tables-c3d10`.
6. **Setup.** Under each of the four fields of a material, "Vary … with temperature" opens a small table: a unit choice over each column (the system's temperature unit and the single value's unit to start with), two empty rows, "Add a row", a remove button per row, "Remove the table", and for expansion the "Measured from" temperature. The material's tree mark lists what a table it uses still needs. Library materials have no tables (MIL-HDBK-5G prints these as curves; parked with the other library extensions).
7. **Verification.** V-19, a wall between 400 °C and 20 °C whose four properties are all tables in mixed units, held sideways between frictionless walls and free to grow through its thickness: the heat flux (conductivity at the mean temperature times ΔT / L, since k is linear), heat flows, the exact profile at three depths, the sideways stress −E(T) ε(T)/(1 − ν(T)) at four depths with ε from the mean coefficients, a stress-free temperature of 50 °C and a reference of 20 °C (so both terms of item 4 count), the growth of the hot face and the force on one wall. `worker/spikes/heat_check` adds the bar with a conductivity table, every node against the exact profile.

### ADR-069: Bonds carry heat: each tied node's temperature follows the other face at the same closest point, and the reader adds the heat CalculiX leaves out of held nodes
2026-10-16 · Accepted (under Shubham's standing M5 autodrive instruction; reviewed and accepted by Shubham on 2026-10-16).

M5.6 lets bonds carry heat (PLAN M5.6), so thermal and thermal stress setups with bonded bodies run instead of being refused (ADR-064 item 5, ADR-067 item 5, which this replaces). Choices it needed:

1. **Temperature ties with the displacement ties' weights.** For every bond not removed (ADR-059), each node of the slave face (the finer mesh, ADR-060) gets one `*EQUATION` on degree of freedom 11: its temperature equals the master face's at the point closest to it, the master nodes' shape functions there times their temperatures. Same closest point, slave choice and tolerance as the displacement ties, so a linear temperature field passes a bond exactly (unit test) and the heat crosses between unmatched meshes. Perfect thermal contact: no contact conductance or gap resistance (not in scope; a thin layer can be modelled as a body). Written as equations, not `*TIE`, for the same reason as ADR-060 (item 3).
2. **A slave node at a fixed temperature is not tied.** Its temperature is given, so an equation would make it depend twice. Supports play no part in temperature ties, and temperature and displacement ties are separate families: a node tied for its displacement may be a master for its temperature. Nodes where three bodies meet are left untied as for displacements, which locally insulates them.
3. **The heat the ties pass to held nodes is added back.** CalculiX's nodal heat flow `RFL` at a fixed-temperature node that tied nodes follow leaves out the heat that reaches it through the equations, as its nodal force leaves out tie forces (ADR-060). Checked with ccx 2.21 on two bonded blocks with a fixed temperature on the master body's face next to the bond: the heat balance read 20 % (C3D4) and 9 % (C3D10) out without it, 1e-8 with it; in the deck snapshot `heat-bonded-c3d10`, where the fixed temperature holds every master node, `RFL` there is rounding (1e-15 W) and all 0.0648 W comes from the ties. The deck prints `RFL` at every tied node (`NSET=TTIED`); the reader takes each one's residual (`RFL` less the heat loads apply there) and passes it to its master nodes by minus their coefficients (`tie_heat`).
4. **Each group of bonded bodies needs one load that sets its temperature.** A fixed temperature, convection or radiation on any body of a group of bodies joined by tied bonds sets the temperature of all of them. Pre-run validation names each group none reaches, and offers restoring a removed bond, as for unheld bodies (ADR-061); the Bodies rows mark such bodies; the deck generator refuses the same.
5. **Decks unchanged elsewhere.** Thermal decks with bonds were refused before, so every earlier deck is byte-identical and DECK_FORMAT stays 5; new snapshots `heat-bonded-c3d10` and `thermal-stress-bonded-c3d4`, and ccx fixtures of both.
6. **Verification.** V-27, a quarter tube of two bonded layers of different conductivity, the outer meshed finer, against the composite cylinder: temperatures in each layer and on both sides of the bond, radial flux in each layer, heat flow in and out. V-14, the single-layer tube listed for M5 but not written until now, is added beside it. `worker/spikes/heat_check` adds a bar cut into two bonded bodies of different conductivity and stiffness: every node against the series wall (fixed temperatures; convection), the same as thermal stress (stress and displacement at every node), and the heat balance with a fixed temperature next to the bond. E-03 runs its bonded model as a thermal stress analysis whose heat must cross the bond.

### ADR-070: Modal analysis: a frequency step on the held bodies, frequencies signed in Hz, free bodies allowed with SPOOLES
2026-10-16 · Accepted (under Shubham's standing M6 autodrive instruction; reviewed and accepted by Shubham on 2026-10-17). ADR-072 replaced items 3 and 4's PaStiX rule: modal setups take SPOOLES alone.

M6.1 adds the modal analysis type (PLAN M6.1: number of modes, supports only). Choices it needed:

1. **Spec.** `analysis: "modal"` and `modes`, a whole number from 1 to 100 (null until entered; switching to modal in the setup enters 10). A modal setup takes supports and no loads: loads stay in the spec and are marked as having no effect, like supports in a steady-state thermal setup, and its Loads group is hidden once they are deleted. Every material needs Young's modulus, Poisson's ratio and the density.
2. **Deck.** `*FREQUENCY, SOLVER=` with the number of modes on its data line and no frequency range, the supports' `*BOUNDARY` lines without values, and `*NODE FILE` `U` for the mode shapes M6.2 will draw. Elastic supports keep their springs, prescribed displacements hold their set components, frictionless supports their normal. A prescribed displacement other than zero is refused, since CalculiX zeroes it silently: a modal analysis finds vibrations about the held position. No reaction or tie sets are printed. Every earlier deck is unchanged; DECK_FORMAT stays 5.
3. **Iterative solvers are refused.** CalculiX 2.21 stops on `*FREQUENCY` with either iterative solver, so pre-run validation and the deck generator ask for PaStiX or SPOOLES. The spec keeps the user's solver choice (ADR-063); nothing switches it silently.
4. **A body no support holds is allowed, with SPOOLES only.** Its six rigid-body modes come out at or near zero (V-22: below 5e-5 of the first elastic mode), which is a check of the model rather than an error, so the rigid-body check of ADR-039 and ADR-061 is skipped for modal. CalculiX's Lanczos factors K − 1·M (arpack.c, shift 1), which a free body makes indefinite. SPOOLES pivots and solves it; PaStiX gave a wrong first elastic frequency (39.96 Hz for 64.86 Hz on V-22's bar) at 4 mm and aborted at the size V-22 ran on the platform. So with PaStiX, pre-run validation and the deck generator refuse a setup that leaves a body free to move (the deck generator by the same rigid-body check as a static setup) and ask for SPOOLES or more supports. A body held only by weak elastic supports, with a mode below 0.16 Hz, would make the matrix indefinite too; not caught.
5. **Frequencies signed, in Hz.** The reader takes the eigenvalue table of the `.dat` file. `SolveResult.frequencies` holds each mode's frequency in Hz, the lowest first, as sign(λ) √|λ| / 2π, so a rigid-body mode that rounding puts below zero reads as a small negative number rather than an imaginary one. The Run panel lists them and notes rigid-body modes when one is within 1e-4 of the largest. units.json version 8 adds the `frequency` kind (Hz, kHz, cpm); each system shows Hz.
6. **Frequencies only until M6.2.** A modal run's `fields.bin` and `nodes.bin` hold no fields, the viewer shows the geometry, and the run has no export; the mode shapes, their display and the frequency table come with M6.2 (since ADR-071).
7. **Estimator and limits unchanged until M6.3.** A modal run is estimated with the linear static law and the same element limits per solver. It needs more memory: V-20's bar at 2 mm (113,748 nodes) ran out of the verification worker's 4 GB with PaStiX, so the full tier of V-20 and V-21 meshes at 3 mm. M6.3 fits the modal terms.
8. **Verification.** V-20 (cantilever), V-21 (fixed-fixed beam) and V-22 (free bar, SPOOLES), an 800 × 16 × 8 mm steel bar against Euler-Bernoulli. V-21 is VERIFICATION.md's fixed-fixed beam; PLAN.md's "simply supported plate" was corrected to match. The bar's shear deformation, rotary inertia and clamped Poisson contraction differ from the beam theory by up to 0.16 %, so the tolerances are 0.5 % (coarse) and 0.3 % (full). The harness gains the `frequency` quantity with a `mode`, and `relativeTo` for a zero reference. `worker/spikes/modal_check` solves the three bars with SPOOLES at 4 mm and 2 mm.

### ADR-071: Mode shapes: one field per mode, scaled to a largest displacement of 1 and signed, drawn at a tenth of the model's size and swung in the shader
2026-10-16 · Accepted (under Shubham's standing M6 autodrive instruction; reviewed and accepted by Shubham on 2026-10-17).

M6.2 adds the frequency table and the mode shape display and animation (PLAN M6.2). Choices it needed:

1. **One field per mode.** The reader takes every `DISP` block of a modal run's `.frd` file, one per mode, and writes each as a field `mode1`, `mode2` … of `fields.bin` and `nodes.bin` (kind `ratio`, three components), so a cut plane fetches one mode at a time like any field. 5. **Animation in the vertex shader.** A swinging mode shape moves the model, its outlines and a cut plane's section from the deformed shape through the undeformed one to the opposite shape and back, once every 1.6 s whatever the frequency, as a `swing` attribute times a shared phase in the vertex shader, so a frame costs no work on the CPU. Min and max markers and probes are hidden while it swings, since they mark the drawn shape.
6. **Saved views keep the mode.** `modeShape` joins view.schema.json's quantities, with an optional `mode`, so M7's report can draw a chosen mode from a saved view.
7. **Verification.** V-20 gains three checks of the cantilever's shape at mid-span against Euler-Bernoulli, φ(L/2)/φ(L): the first bending modes in z and y (0.3395) and the second in z (−0.7137, which also checks the sign). The harness gains the `modeShape.x`/`.y`/`.z` quantities with a `mode`.

### ADR-072: Modal runs are solved with SPOOLES alone and estimated with a part per mode; modal element limits are for 100 modes
2026-10-17 · Accepted (under Shubham's standing M6 autodrive instruction; reviewed and accepted by Shubham on 2026-10-17). The SPOOLES-only choice was put to him on a decision card in the M6.3 thread and built on its recommended option while it waited.

M6.3 adds the estimator terms for modal runs (PLAN M6.3; ADR-070 item 7 left them for it). Choices it needed:

1. **PaStiX is not used for modal runs.** Benchmarking modal runs with the worker image's build, PaStiX aborted with "Fatal glibc error: malloc.c:4376 (_int_malloc): assertion failed" on a fully held block of 37,725 nodes (24,989 ten-node elements) in 3 of 9 tries that shared nothing with another run, with 1 to 100 modes; static PaStiX runs of the same mesh never did, and 19,000-node and 6,000-node modal meshes finished every time. Valgrind (`memcheck`, 5,693 nodes, a run that finished) shows an invalid 4-byte write into memory Scotch had freed, in `pastix_factor_main_generic` called from `arpack`: CalculiX's own PaStiX interface (`pastix.c`) writes through a stale pointer on the frequency step, so how the heap lies decides whether a run crashes. V-20 and V-21, which named no solver, now name SPOOLES. Fixing the interface means patching CalculiX's `pastix.c` in `worker/ccx/build.sh`, its own pull request with a full verification run; it is parked. SPOOLES was 1.6 times slower than PaStiX on the 37,725-node mesh with 10 modes (93 s against 58 s).
2. **A part for the mesh and a part per mode.** CalculiX's Lanczos (ARPACK) keeps a set of vectors that grows with the modes asked for and solves with the factorised matrix once per iteration, so memory and time grow with the modes: on the 37,725-node mesh, 1.0 GiB and 51 s with 1 mode, 1.33 GiB and 526 s with 100. Each is fitted as `mesh part + modes × part per mode`, each part a power law in the node count (`estimator.json` version 4, `analyses.modal.spooles`): memory 105 MB + 476 × n^1.376 bytes plus 104 × n^1.001 bytes per mode, time 0.33 s + 1.15e-7 × n^1.895 s plus 0.065 s + 1.75e-7 × n^1.633 s per mode. Each mesh's two parts are the line through its runs with 1 and with 100 modes; between them both quantities bend upwards (memory does not grow at all below about 10 modes), so the line is above the measurements there. `steps.py` gained `--analysis modal --modes N` (the M2.11 block held at one end, no load, density 7,850 kg/m³); `steps.json` has 26 modal rows, 11 meshes from 5,212 to 207,025 nodes at 1 and 100 modes and the 37,725-node mesh at 10 and 50 as well. Fitted memory is within 5 percent of every row and time within 18 percent. A modal run of 145,471 ten-node elements with 100 modes took 8,710 s and 11.0 GiB, against 1,518 s and 8.9 GiB for the same mesh static.
3. **The estimate is for the modes asked for; the limits are for 100.** The estimate before a run uses the spec's modes (the most, 100, while none is entered) and says so ("Estimated for this mesh's N nodes and M modes"); `RunEstimate` gains `analysis` and `modes`, and `GET /api/simulations/{id}/estimate` takes `?analysis=` and `?modes=` beside `?solver=`, so the panel follows an unsaved change. The element limits are worked out as ADR-063 item 5 says, for 100 modes, so one limit per order holds for every modal run: 136,000 ten-node elements and 461,000 four-node ones (the 500,000-element stop again), against SPOOLES's 161,000 and 461,000 for a static run. A limit per number of modes would let a 10-mode run take more, but would turn each limit into a table and the Run panel's list into a function of a field elsewhere; with 10 modes the same rule gives about 156,000 ten-node elements by memory, which the largest mesh measured (145,471) would cap, so at most 7 percent more. A modal run above its limit is refused with "… more than the 136,000 SPOOLES can solve in a modal analysis of up to 100 modes on a 16 GB machine …".
4. **The Run panel.** For a modal setup the solver list shows SPOOLES with its modal limit and the others as "not for modal analysis", and the limits note says they are for 100 modes. `runSolvers`, `runSolverProblem` and `specRunKind` in `packages/spec` say which solvers a run of an analysis can use and why not; the estimate endpoint answers a solver that cannot solve a modal run with that reason (409).
5. **Thermal runs still use the linear static model** (ADR-064 item 7): one unknown per node instead of three, so their estimate is high, the safe side.
6. **Verification.** No physics changed for a run that was already allowed: V-20, V-21 and V-22 pass on SPOOLES (`make verify`, coarse, 31 of 31). `worker/tests/test_estimator.py` checks that the fit recovers a known part per mode and that every modal mesh measured under a modal limit, at any number of modes, fits 16 GiB with the margin.

### ADR-079: Rounding noise in the report's reaction and balance tables prints as 0
2026-10-17 · Accepted (Shubham's decision at the M7 close: "Round those values to 0").

The report printed stored sums that are zero as the solver's rounding noise, for example an applied force component of -1.791e-15 N or a V-02 reaction of Fx = -0.00003084 lbf against a 500 lbf load, which also wrapped in its narrow table cell. Choices it needed:

1. **Relative to the run's own balance scales.** A force component prints as 0 when its size is below one millionth (`NOISE_SHARE`, `worker/clearfea_worker/report/content.py`) of the run's balance check `forceScale`, and a moment component when below one millionth of `momentScale` (ADR-051): the scales the balance check already measures imbalance against, so the rule follows the size of the loads and of the model. One millionth is far below the 0.1 percent the verification cases hold reactions to and above the noise of the direct solvers (V-02's is about 3e-8 of its scale); the iterative solvers' noise (relative residual 1e-4, ADR-063 item 8) can stay above it and print, which is honest for them.
2. **Where.** The reactions table, the load totals table and the applied and reaction vectors of the balance table. The out-of-balance percentages are computed from the stored values as before and print unrounded, since they are the measure of the noise. A paragraph under the balance table says that components below one millionth of the scales print as 0. Nothing stored changes: the run's result, the app's panels and the exports keep the values as solved.
3. **Runs without a balance check** (solved before M3.2) have no scales, so their values print as stored.
4. **Verification.** No physics-critical module is touched: printing only. A worker test checks that noise prints as 0, a small real value still prints, and no exponent is left in the section.

It shows the balance, granted and charged, a note on what is charged (per started second at the queued size's rate; import and mesh reuse free; ClearFEA's faults not charged; a run refused above the balance) and one row per entry with the time (UTC), what it was for, the machine size and rate, the billed seconds, the amount and the balance after it. The Run panel keeps each run's own cost (ADR-033 item 8).
3. **A grant is a ledger entry written by the seed.** `apps/api/seed/test-users.sql` gives each test user one play-money grant of 100 credits (reason `grant`, no job) when they have none, so running the seed again adds nothing. At the placeholder rates (0.5 to 4 credits an hour, ADR-049 item 4) that is 25 to 200 hours of machine time. No route writes a grant; the beta's monthly grant (DECISIONS "Beta") comes with real accounts in Phase 1.
4. **A run its balance cannot cover is refused before it is queued.** `POST /api/simulations/:id/runs` refuses (409) a run whose estimated cost on the size it would go on is more than the balance, saying both amounts and what to do (`apps/api/src/billing/wallet.ts`). Meshing has no estimate, so a new mesh is refused only when the balance is 0 or less; reusing a mesh is free and always allowed. The check reads the balance once, so two runs started together can both pass and a run can cost more than its estimate: the balance may still go below 0, as before, and the stop limit (M8.3) bounds a run's cost. Self-hosting mode (M8.10) is where the refusal is turned off.
5. **One formatter.** `credits()` moved from the web app to `packages/spec`, so the API's messages write amounts as the page does.
6. **Verification.** The billing arithmetic (`cost.ts`) and the charge statement are unchanged; the ledger module gains reads only. API tests check the wallet's entries and totals, the owner scoping, the seed's single grant, and both refusals; a web test opens and closes the page. `make verify` and `make e2e` run as the seeded users, whose grant covers them.

### ADR-081: The estimator check prices every benchmark row as a run is priced; job time is fitted per element order; one billed second counts as within the margin
2026-10-17 · Accepted (under Shubham's M8 autodrive; the refit and the one-second allowance were his choice on a decision card).

M8.9 checks the estimate against measured cost on the benchmark set (PLAN M8.9; DECISIONS gate condition 3 and its working tolerance of 30 percent). Choices it needed:

1. **What is compared.** `worker/benchmarks/solver/check.py` takes every row of `steps.json` (the job-step benchmark, ADR-049, ADR-063, ADR-072) and prices it as the platform prices a run: the estimate is the fitted job time rounded up to whole seconds (`estimateMesh`), the measured cost the row's job time rounded up to whole seconds (`billedSeconds`). Both are the same rate times those seconds on every machine size (`costOf`; the solver has one thread on every size, ADR-048), so the cost's relative error is that of the billed seconds on every size, to a micro-credit. The check is in-sample: it uses the rows the fit was made from, as the gate asks ("on the benchmark set").
2. **The margin.** A row passes when its estimated cost is within 30 percent of its measured cost, or within one billed second. Billing per started second makes one second more than 30 percent of any job billed for 3 seconds or less (a 2.0 s modal run estimated at 2.1 s is billed 2 s and estimated at 3 s, +50 percent), and no fit can close that.
3. **Job time per element order (estimator version 5).** With one time law for both orders, 66 of 69 rows passed: iterative scaling was +31 and −30.4 percent (its iterations depend on the element order), and the 2-second modal row was +50 percent. `AnalysisModel.jobSeconds` is replaced by `jobSecondsByOrder` (`order1`, `order2`), each fitted over that order's rows; `estimateMesh` and `estimateRun` take the mesh's element order. Memory stays fitted over both orders, so the element limits (ADR-063) and recommendations are unchanged. The modal model is unchanged (its rows are almost all ten-node). Per solver now: PaStiX −14 to +15 percent, SPOOLES −9 to +11, iterative Cholesky −9 to +9, iterative scaling −13 to +24, modal SPOOLES −14 to +50 (one second). All 69 rows pass. Each order's law rests on 4 to 7 rows.
4. **In the fast tier.** `worker/tests/test_estimator.py` runs the check, so a refit that misses the margin fails `make test` beside the existing "estimator.json is the fit of steps.json" test.
5. **The platform, checked once by hand.** The M2.11 block went through the platform (API and worker container as `make verify` runs them) on 16 meshes and solvers, comparing each run's frozen estimate with its billed seconds. Within 30 percent or one second on 14: PaStiX −33 (one second) to +16 percent, iterative +5 to +25. Two SPOOLES runs were overestimated, the safe side: +34 percent at 37,725 nodes (51 s estimated, 38 s billed) and +32 percent for 100 modes at 18,866 nodes (189 s, 143 s). In the container SPOOLES ran 20 to 25 percent faster than the benchmark on the host, while PaStiX's small runs took 1 to 2 s longer (the job's downloads and uploads, which `steps.py` does not time). Re-measuring `steps.json` inside the worker container would remove that difference; parked.
6. **The verification suite.** `make verify` now lists each case's estimated and billed solve seconds next to its mesh line and in `results.json`, as information only and not as a check. CI machines are not the benchmark machine, and the estimate stays high for slender parts (ADR-049 item 3; no shape term is added). On the coarse tier here (302 of 302 checks) 21 of the 23 static and thermal cases were estimated within one second of their bill (V-01 was 7 s against 5 s, V-04 20 s against 15 s), and the three modal beams 21 to 30 s against 5 to 8 s: their modal model was fitted on the stocky block at 1 and 100 modes.

### ADR-082: A machine size is simulated by holding the solver to its cores and stopping it past its usable memory; the API decides who pays for running out of memory
2026-10-17 · Accepted (under Shubham's M8 autodrive, pending his review).

M8.5 simulates the machine sizes on one physical machine (PLAN M8.5; ARCHITECTURE "Metering": "it sets the solver thread count and a memory limit on the solver process") and builds the out-of-memory path that DECISIONS "Failed runs" asks for. ADR-049 item 5 and item 7 left both for this task. Choices it needed:

1. **The solve job carries its machine.** `SolveParams` gains `machine` (`SimulatedMachine`: size, cores, `memoryLimitBytes`), frozen into the job when the run is queued (`simulatedMachine` in `apps/api/src/billing/estimate.ts`). Jobs queued before M8.5 have none and run unlimited. Mesh, import and report jobs are not limited: meshing goes on the default size the platform picks, so its running out of memory would be the platform's fault either way.
2. **Cores, not threads.** The worker holds the solver process to the size's number of processors (the first ones the worker may use; all of them when the size has more) with `sched_setaffinity`. The solver itself stays on one thread on every size (ADR-048 item 3, ADR-063 item 3), so a run takes the same time on every size and the estimator is unchanged; more threads on larger sizes would change answers (threaded SPOOLES) or times, and is a decision for when larger machines are benchmarked.
3. **The memory limit is the size's usable memory.** `memoryLimitBytes` is the size's memory times the estimator's `usableMemoryFraction` (0.85), the share the recommendation counts on (ADR-049 item 5) and the share the benchmark sandbox had of its machine. A recommended size therefore stops a run only when the estimate is short by more than its 1.25 margin.
4. **Stopped like the kernel would.** The worker reads the solver's resident memory from `/proc` every 0.1 s (it also polls for a cancel at that rate now, was 0.5 s) and kills it with SIGKILL once it passes the limit: no warning to the solver and no clean-up, as the out-of-memory killer on a real machine of that size. Resident memory is what the benchmark measured (`ru_maxrss`). A solver killed by SIGKILL that the worker did not send is also reported as out of memory: that is the real machine's (or container's) killer, reached first when a simulated size is larger than the machine. A size larger than the physical machine is still not simulated faithfully; on localhost the real machine's memory is the ceiling.
5. **The worker reports the cause; the API decides who pays.** The worker fails the job with cause `out_of_memory` (keeping the deck and log) and leaves the category to the API, which alone knows the run's frozen estimate. The user pays when the size was chosen against the platform: it is not the size the platform would have put the run on (the recommended one, or the largest when none fits) and by the estimate its memory does not fit. Otherwise (the recommended size, a larger one, or any size the estimate says fits) the platform's estimate was wrong and it pays (`outOfMemoryFault`). This is ARCHITECTURE's "smaller than recommended" with the case of no recommendation settled. The run says which, in plain words, with what to do: the recommended size, or a larger one.
6. **The Run panel says it.** The note on a size with too little memory now also says that the time used is then charged.
7. **Verification.** No deck, load or result code is touched; the billing module gains two pure functions and the charge rule itself (`isCharged`) is unchanged. Worker tests stop a stand-in solver past its limit and hold one to its cores; API tests check the job's machine and who pays on the recommended, a larger, a fitting and a too-small size. A real CalculiX solve stopped by the limit and the same deck solved under a larger one were checked by hand (PR description).

### ADR-083: A run has at most one read-only share link; only its token's hash is stored, and the link opens the run's results alone
2026-10-17 · Accepted (under Shubham's M8 autodrive, pending his review).

M8.7 adds the read-only share link per run (PLAN M8.7; DECISIONS "Privacy": read-only share link per run, revocable; ARCHITECTURE section 10: share links carry a random token, only its hash is stored). Choices it needed:

1. **One active link per succeeded run.** `POST /api/runs/:id/share` makes a link for the owner's succeeded run and answers its token (32 random bytes, base64url); a solving or failed run has nothing to share and is refused (409). Making a link again replaces the earlier one, which stops working. `GET` says whether a link is active and when it was made; `DELETE` revokes it, deleting its row (`share_links`, migration 0017). Several links per run, named or expiring, would need more UI for no stated need.
2. **Only the hash is stored, so the link is shown once.** The table holds the token's SHA-256; the Run panel shows the link when it is made, with a copy button, and afterwards only that a link made at a given time is active, with "Make a new link" (which revokes the old one) and "Revoke the link".
3. **The link opens the run's results and nothing else.** `/api/shared/:token` needs no sign-in and answers the run's frozen setup, mesh, versions and results (`SharedRunView`), the simulation's name and the owner's unit system; `/topology`, `/surface`, `/fields`, `/mesh` and `/nodes` serve what the result view draws, through the same code as the owner's routes. The owner's machine size, estimate and cost, the solver input and log, the report and every other record stay the owner's. A revoked, replaced, mistyped or made-up token answers 404 with one message ("This share link does not work…"), so a token reveals nothing. The token lookup is the one data-access function without a user id: it answers the owner and run the token was made for, and the run is then read through the owner-scoped functions.
4. **The page.** `/share/<token>` opens a page with the run's record (simulation name, analysis, times, mesh, versions) on the left, the viewer in the centre and the Run panel's results on the right (`RunResults`, the same component): quantity, shape, display units, figures and notes. The viewer reads the run's files through the link (`ViewerSource`); saved views, export and everything that edits are absent. Choices made there are kept until the page is reloaded and are not stored.
5. **Tests.** API tests cover making, replacing and revoking a link, the stored hash, what the link serves and refuses, and that only the owner can manage it. E-07 (`e07-share-link.e2e.ts`) opens a link in a browser that is not signed in, checks that bob reaches none of alice's geometry, simulation or run, revokes the link and finds it no longer works. The full isolation sweep across every route and file key is M8.8's.

### ADR-084: Self-hosting mode is one API variable; it keeps metering and charging, and turns off the refusals
2026-10-17 · Accepted (under Shubham's M8 autodrive, pending his review).

M8.10 adds the self-hosting flag (PLAN M8.10: wallet informational; DECISIONS "Self-hosting": wallet and metering off or informational). ADR-080 item 4 left turning the refusals off to this task. Choices it needed:

1. **One variable on the API.** `SELF_HOSTED=true` (or `1`, any case) in `apps/api/.dev.vars` turns the mode on (`apps/api/src/selfHosting.ts`); unset or anything else is the hosted mode. Only the API decides anything from it, and the web app learns it from the wallet route, so there is one place to set it. `.dev.vars.example` carries the line commented out.
2. **Informational, not off.** Jobs are metered and charged to the ledger exactly as when hosted (the billing module is unchanged), so a self-hoster sees what each mesh and run cost and what the same work would cost on the hosted service. Turning metering off would remove the run's cost from the run record and the wallet for no gain.
3. **Nothing is refused for its balance.** The run route skips `runFundsProblem` and the mesh route `meshFundsProblem`, so the balance can go below zero and stays there. The seed's grant is unchanged. Refusals that are not about money (element limits, a run already solving) stay.
4. **The page says it.** `WalletResponse` gains `selfHosted`; the wallet page then replaces the "play money … a run is refused" note with one saying the wallet is information only and nothing is refused.
5. **Tests.** API tests run the app with `SELF_HOSTED` set (`app.request` with the test bindings plus the variable) and check that the wallet says so, that a run the balance cannot cover is queued and charged below zero, and that a mesh is made at a zero balance; the hosted refusal tests are unchanged. A web test shows the self-hosted note.

### ADR-085: A run is cancelled by asking its worker at the next heartbeat; the worker reports the time it used and the owner pays it, and a run cancelled before the worker takes it ends at once and costs nothing
2026-10-17 · Accepted (under Shubham's M8 autodrive, pending his review).

M8.2 adds the running-job view and cancel (PLAN M8.2; DECISIONS "Running jobs" and "Failed runs": the user pays for time used on a cancellation; ARCHITECTURE section 6). Choices it needed:

1. **A cancel is a request on the job, settled by the worker.** `POST /api/runs/:id/cancel` sets `jobs.stop_requested` to `cancelled` (migration 0018, with `stop_requested_at`); the job stays `running`, so the worker still holds it. Its next heartbeat (every 5 s) answers `cancel`; the worker stops CalculiX (terminated, killed after 5 s, as since ADR-030), uploads the deck and the log so far, and completes the job with a new `status: "stopped"` and its metering (`CompleteStopped` in `jobs.schema.json`). The API then ends the job with the status that was asked for. Setting the job's status to `cancelled` at once, as the heartbeat code allowed since M0, would leave the worker no way to report its time, and DECISIONS says a cancellation is paid. A `stopped` completion for a job nobody asked to stop is refused (409).
2. **The time used is charged.** `isCharged` (`apps/api/src/billing/cost.ts`) charges `cancelled` and `stopped_at_limit` jobs like a success: billed seconds of the handler's time at the job's rate, in the same batch that completes it (ADR-033). The run says "You cancelled the run after 13 s. The time it used is charged. Run it again for results."
3. **A run still queued ends at once, free.** If no worker has claimed the job, the same request ends job and run in one batch: job `cancelled` with 0 billed seconds and cost 0 (not charged), run ended with "You cancelled the run before the solver started, so nothing was charged." A worker can no longer claim it.
4. **A result that beats the cancel stands.** The solver checks for a cancel every 0.1 s while it runs and the solve handler before it starts; reading results and uploading are not interrupted. A job that finishes before the worker hears of the cancel reports its result, and the run succeeds and is charged as usual: the results exist and the time was used either way.
5. **Cancelled is a run status, kept in the job.** `RunStatus` gains `cancelled`. The `runs` table keeps `failed` for every run that ended without results (its CHECK constraint cannot be changed without rebuilding the table, which `report_figures` and `share_links` reference with cascading deletes); a run reads as `cancelled` when its job is. The wallet's run status does the same. In the tree a cancelled run is incomplete, not an error, with its message.
6. **What the running view shows.** `RunView.progress` (null once the run has ended) holds when the worker took the job, the time since then when the answer was made, the cost of that time so far (per started second at the run's rate, from the claim, so up to about a second above what the handler's metering will bill) and whether a cancel is pending. The Run panel shows the stage, "Elapsed 1:05 of about 1.9 min estimated", "Cost so far … of about … estimated" (the run's frozen estimate on its machine size), the live log as before, a "Cancel the run" button and that the run carries on if the browser is closed. The clock ticks every second in the browser between the API's answers (every 2 s); while a cancel is pending the stage reads "Cancelling…" and the button is disabled. No confirmation step: a cancel costs at most the time already used.
7. **Room for the stop limit.** `stop_requested = 'stopped_at_limit'` makes the heartbeat answer `stop` and the stopped job end as `stopped_at_limit`; M8.3 needs only to decide when to set it and what the run says. E-06 (`e06-running-job.e2e.ts`) builds its slow run (the E-01 block at 1 mm, quadratic, SPOOLES, about two minutes) in a helper the stop-limit test can share.
8. **Not done here.** Meshing cannot be cancelled (no route asks; the mesh handler does not check). A worker that dies leaves its job running and a pending cancel unanswered, as any stalled job is today (no heartbeat timeout yet).

### ADR-086: Storage is measured from the stored files; a daily sweep removes unpinned raw output after 30 days and charges storage above a 5 GiB allowance once a day; a rerun of the run's own setup regenerates removed output
2026-10-17 · Accepted (under Shubham's M8 autodrive, pending his review).

M8.6 adds storage accounting, the free quota, retention of raw output, pinning and regenerating by rerun (PLAN M8.6; DECISIONS "Storage"; ARCHITECTURE section 4). The quota, retention period and rate are configuration values DECISIONS leaves open. Choices it needed:

1. **Placeholder values, in a `settings` table.** Migration 0019 creates `settings` (name, whole-number value; configuration, like `machine_sizes`, changed with `wrangler d1 execute`): `storage_free_bytes` 5 GiB, `raw_output_retention_days` 30, `storage_rate_per_gib_day` 10,000 micro-credits (0.01 credits per GiB per day, about 0.3 per GiB per month). They are placeholders until beta data sets them. M8.3's stop-limit multiplier can be a row in the same table.
2. **Usage is measured from R2, not kept in a table.** `measureStorage` lists every object under `owners/<id>/` and adds sizes up by kind (geometry, mesh, results, raw output, report; `storageKind` reads the key). Every file a user owns is under that prefix, so nothing is missed and no counter can drift from the files. Listing is paged and cheap at Phase 0 sizes; in the cloud a per-user total kept on write may replace it if listing gets slow. A shared mesh (ADR-047) counts once, under its owner.
3. **Raw output is `results.frd` and `results.dat`.** Nothing reads them after the solve job (the viewer, cut planes, exports, share links and reports use `surface.bin`, `fields.bin`, `nodes.bin`, the deck and the log, all kept permanently), so removing them changes no view. They become downloadable from the run (`GET /api/runs/:id/files/results.frd`, always as an attachment) while they are kept, so retention concerns something the user can reach; a removed one answers 410 with what to do.
4. **A daily sweep does the removal and the charging.** `sweepStorage` runs from the Worker's `scheduled` handler (cron `0 3 * * *` in `wrangler.jsonc`). It removes the raw output of every unpinned run that ended at least the retention period ago, marking the run first (`runs.raw_removed_at`, only while `pinned = 0`) and then deleting the files, so a pin racing the sweep wins and a removed run cannot be pinned. Then it measures each user and, when the total is above the allowance, writes one ledger entry with reason `storage` and a `storage_charges` row (day, bytes used, allowance, rate) in one batch; the row's key (owner, UTC day) makes a day's charge happen once, so running the sweep again changes nothing. `wrangler dev` does not fire cron triggers, so `make dev` runs it with `--test-scheduled` and `infra/dev.sh` calls `/__scheduled` at start and every hour. `make verify` and `make e2e` never run it, so their ledgers hold job charges only and the M8 exit reconciliation is unaffected.
5. **The charge is pure integer arithmetic.** `storageDayCost` (`apps/api/src/billing/storage.ts`): bytes above the allowance × rate ÷ GiB, rounded to the nearest micro-credit (halves up) through BigInt, as job costs are (ADR-033). Measured once a day, not integrated over the day: a file added and removed between sweeps is not charged. Self-hosted mode (ADR-084) still records the charge; it refuses nothing anyway. Being over the allowance refuses nothing either: DECISIONS says it is charged, not blocked.
6. **The pin is a run column that may change.** `runs.pinned` (migration 0019) is the owner's choice about storage, not one of the run's frozen inputs (CLAUDE.md "Runs are frozen"); `PUT /api/runs/:id/pin { pinned }` sets it. `RunView.rawOutput` gives `pinned`, `keptUntil` (end time + retention days; null when pinned, removed or never written), `removedAt` and `rerunOf`.
7. **Regenerate is a rerun of the run's own setup.** `POST /api/runs/:id/rerun` solves the run's frozen spec on the same mesh (meshes are never removed) as a new run of the same simulation, with `runs.rerun_of` naming the old one, so the new raw output belongs to the same results even when the simulation has been edited since. It is estimated, refused for funds and charged like any run, on the old run's machine size while that size exists (else the recommended one); a run is refused while the simulation is solving. The old run keeps its removed state; the new one is the latest run.
8. **Where it shows.** The Run panel gains "Raw solver output": downloads, "Kept until …" or "Pinned", "Pin to keep"/"Unpin", and after removal the date and "Run this setup again". The wallet page gains a Storage section (stored, allowance, above it; a table by kind; the runs holding raw output with their dates and a pin button), and storage charges appear in the ledger as "Storage on <day>: … above the … free allowance". `GET /api/storage` (`storage.schema.json`) answers it.
9. **Verification.** No deck, solver, result or unit code changes. The billing module gains `storage.ts` (pure, unit-tested for rounding, the allowance and sizes past 2^53) and the wallet query a join; job charging is unchanged. API tests cover measurement by kind, owner scoping, pins, the sweep (expired, pinned, recent; files kept; 410 after removal; idempotent), daily charging once per day with the ledger adding up exactly, the scheduled handler and the rerun (frozen spec, same mesh, size, refusals). Web tests cover the Run panel section and the wallet's storage section. No E-test is listed for storage (VERIFICATION lists E-06 and E-07 for M8).
